# プロダクト要求定義書

**この文書は日本語版が正。** 変更したら [`../en/product-requirements.md`](../en/product-requirements.md) も更新する。

> **薄く書く方針。** スコープ・スケジュール・完了条件の詳細は、著者の非公開の計画書にある
> （キャリアに関する個人情報を含むため公開しない）。両者が食い違った場合は非公開の計画書が優先で、
> この文書のほうを直す。

## 解決する課題

バンガロールには日本語を学び始めた人が大勢いる。だが**教科書を読むことと、自分の口で一文を言うことの間には大きな段差がある**。話す相手がいないので、間違えても直してもらえない。教師の数は学習者に対して圧倒的に足りない。

## 何を作るか

初級者が場面を選び、AI と**声で**会話し、会話が**終わったあとに**訂正と短い英語の理由を受け取る Web アプリ。

1. 場面を選ぶ（挨拶／自己紹介／お礼／簡単な依頼／予定と遅れの連絡／職場の敬語）
2. **「会話を始める」** — AI が先に話しかける
3. マイクを押して声で話す → AI が声で返す → 何往復でも続ける
4. **「会話を終える」**
5. **振り返り**：話した文の一覧／直した方がよかったところ／自然な言い方／英語で短い理由

## 意図的に作らないもの

教材・ドリル・試験対策・単語帳・聞き取りクイズ、そして**発音採点**。音声は入力手段であり、直すのは音素ではなく**言い方**である。既存サービスに機能の広さで勝てる見込みはない。

## 利用者

バンガロールで日本語を学び始めた人。Minna Shuugou のコミュニティと個人的なつながりを通じて届ける。携帯のブラウザでリンクを開き、**共有のアクセスコード1本**で入る。アカウント登録は作らない。

**個別のアクセスコードは配らない（2026-08-16 決定）。** 当初は1人1コードにして継続率を測る計画だったが、
**利用者が2〜3人ではどのみち統計にならない**ため、配布と運用の手間に見合わない。
コードの目的は**誰でも触れる状態にしないこと**だけに絞る。

## ユーザーストーリー

1. **日本語を学び始めた人として**、場面を選んで声で話しかけられるので、**日本語キーボードを持っていなくても**練習できる。
2. **学習者として**、会話中は訂正で遮られないので、**間違いを恐れずに最後まで話しきれる**。
3. **学習者として**、会話が終わったあとに自分の言った文と自然な言い方が並んで見え、**英語で理由が読める**ので、なぜ直すのかが分かる。
4. **聞き取りを鍛えたい学習者として**、AI の返事の文字を消せるので、同じアプリのまま耳の練習に切り替えられる。
5. **音声認識に誤って書き起こされた学習者として**、「もう一度」を押して言い直せるので、**打ち直しを強いられない**。
6. **開発者として**、評価データを訂正エンジンに直接流せるので、**アプリや音声認識の影響を受けずに訂正の実力だけを測れる**。

**受け入れ条件**：上記1〜5が、テスターが実機（携帯のブラウザ）で1回のセッションを通して確認できること。6は評価スクリプトの実行で確認する。

## 既存サービスとの差分

最も近いのは `japanesecompass.com`（2026-08-02〜03 に裏取り）。機能の広さでは勝てないので、そこでは戦わない。

**次の2つは差別化にならない。裏取りで確認済み。**

- **向こうの AI 会話も訂正する**（"get gentle corrections"、Pro には "teacher-grade corrections"）
- **向こうにも音声入力があり、発音採点まである**（`/practice/speaking/`）。**こちらは発音採点をしない**

**差は「組み合わせ」にある。** 向こうは音声と会話が別機能で、音声練習は**お手本の読み上げ（シャドーイング）**、AI 会話は**打ち込むチャット**。**声で話すことと、自分の文を作ることが同時にできない。**

1. **自分の言葉を、声で、会話の中で話す**（読み上げでも打ち込みでもない）
   — **定型句をなぞらせると直す対象が消え、評価が成立しない**
2. **訂正を会話中に出さず、終了後にまとめて返す**（向こうは会話中に都度訂正）
3. **訂正の品質を数字で公開している** ← **本命。裏取り済みで、向こうは精度を一切公開していない**
4. 訂正の根拠を文法リファレンスから引く

## 成功の定義（2026年9月20日）

| 指標 | 定義は [glossary.md](glossary.md) | 目標 |
|---|---|---|
| 判定の正しさ | `detection_accuracy` | 85%以上 |
| 余計な直しの率 | `over_correction_rate` | 15%以下 |
| 直しと理由の妥当性 | `correction_validity` | 妥当85%以上（**本人1人の採点**。下記） |
| 採点者の一致率 | `rater_agreement` | **9/13 に取得しにいく。現時点で未取得**（[glossary.md](glossary.md) §5） |
| 検索の当たり率 | `retrieval_hit_rate` | 80%以上 |
| レベル遵守率 | `level_compliance_rate` | 90%以上 |
| 利用 | **数字は出さない。** テスター2〜3人の**感想が3件** | 3件 |

訂正に関する数字はすべて**自作の評価データ120件**で測る。**開発用80件／評価用40件**に分割し、**素朴な1回呼び出しのベースラインと並べて**報告する。

**期限を11月末から 9/20 へ前倒しした（2026-08-18）。** 稼働が週6.5時間から**毎日2時間＝週14時間**に戻ったため。
その前は8月末から11月末へ延ばしていた（2026-08-16、稼働が週26時間から週6.5時間に落ちたとき）。
**指標そのものと目標値は、いずれの改訂でも1つも変えていない**——変えたのは期限と、下の「測らないと決めたもの」だけである。

### 測らないと決めたもの（2026-08-16）

**目標に届かないことより、測ったふりをすることのほうが評価を壊す。** 降ろしたものは隠さず書く。

| 降ろしたもの | 当初の定義 | 理由 |
|---|---|---|
| **応答時間**（`latency_ms`） | 中央値と95パーセンタイルを、音声段の有無で分けて、改善前後で比較 | 計測の仕込みと最適化に時間が要り、**主要3指標には触れない**。README には「測っていない」と書く |
| **利用者数・継続率** | 1回以上会話したテスター5人以上、1人あたりターン数 | 利用者が2〜3人では統計にならない。**保存もしないので取得経路が無い**（[architecture.md](architecture.md) の「保存しないという決定」） |
| **音声認識の精度・通しの精度** | 録音30件をネイティブが耳で書き起こして比較 | **音声を保存しない**と決めたため、材料が手に入らない |

**紛らわしいので1つ書き分けておく。** 「測らない」のは**公開する指標として**であって、
`evals/score.py` は評価実行の所要時間（`elapsed_ms` / `latency_ms`）を**実行記録には残している**。
これは**アプリが学習者について記録するものではなく、評価スクリプトが自分の実行について残す記録**である。
**README には出さないし、最適化もしない。** ここを曖昧にすると「測っているのに測っていないと書いた」
ことになるので、コード側のコメントにも同じ断り書きを置いてある。

**「もう一度」の押下回数も取れなくなった。** 音声認識の質を測る目安として設計に入れていたが、
保存しない以上どこにも残らない。**画面のボタンは残す**（学習者に打ち直させないためのもので、目的が別）。

## 非機能要件

- `docker compose up` でローカル起動できる
- 秘密情報は環境変数。1日あたりのトークンと音声合成の上限を実装する
- 機密情報を話さないよう促す注意書き、**AI の合成音声であることの明示**、**連絡先**
  （~~削除依頼の受け口~~ → **保存しないので削除するものが無い**。連絡先だけを出す）
- **学習者の発話・音声・訂正結果をどこにも保存しない。** 氏名も保存しない。
  **保存しないので同意記録も持たない**（注意書きだけを出す）
