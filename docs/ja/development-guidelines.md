# 開発ガイドライン

**この文書は日本語版が正。** 変更したら [`../en/development-guidelines.md`](../en/development-guidelines.md) も更新する。

> **薄く書く方針。** 既に決まっている規約のみ。コードが増えて根拠ができてから広げる。

## 言語・ツール

- Python 3.11 以上（**現在 3.12.13**）。環境は **`uv`** で管理する
  — `uv sync` で依存を入れ、`uv run <cmd>` で実行する。システムの Python は触らない
- `ruff`（リント・整形）と `mypy`（型チェック）— コードを変更したら必ず両方を実行する
- 公開関数には型注釈を付ける

## 命名

- 関数・変数・モジュールは `snake_case`、クラスは `PascalCase`
- **コード上のフィールド名は JSON のキーと完全に一致させる**（`needs_correction` / `corrected_sentence` / `reason_en` / `grounding_ids`）。評価データとコードが乖離しないようにするため
- ドメイン用語は [glossary.md](glossary.md) に従う。**同義語を作らない**——「訂正」を fix や suggestion や feedback と呼び替えない

## 構造

- 責務ごとに1モジュール：`dialogue/` `correction/` `retrieval/` `nlp/` `evals/` `app/` `api/`
- プロンプトは各モジュール内の別ファイルに置き、版を管理する。**評価の実行記録には、どの版のプロンプトで出た数字かを必ず残す**
- 訂正ノードは**構造化出力**を返す。自由文をパースする実装は認めない

## テスト

- `pytest` を使う。**確定処理には必ずテストを書く**：検証ノード、編集距離、語彙レベル判定、評価の採点
- **採点スクリプト自体にもテストを書く。** 採点の不具合はモデルの改善と区別がつかない
- 実行のたびに評価用から**5件を手で照合**する
- モデルを呼ぶコードは、記録済みの応答に対してテストする。実際に呼ばない

## 評価の規律

- プロンプトと閾値の調整は**開発用データだけ**を見て行う。評価用は8月の最初と最後にしか触らない
- 実行のたびに記録を残す：モデル名、プロンプトの版、日付、データ分割
- **公開するすべての数字に `n` と誤差の目安を併記する**

## 見た目

CSS のみ。フレームワークは使わない。背景は生成り、文字は墨、差し色は1色だけ、見出しは明朝系、余白を広く、罫線は細く、影は使わない。**鳥居・桜・忍者・赤×金は避ける**——和風のクリシェは一瞬で安っぽく見える。引き算で作る。

## ドキュメントの自己点検

`docs/` を更新したら、以下を当てて読み直す。**書いた直後ではなく、翌朝に当てる**——書いた直後は自分の意図が頭に残っているため、抜けが見えない。

Claude に点検させる場合は「このドキュメントを次の6観点で点検し、問題と推奨を挙げて」と指示する。**書き直させるのではなく、指摘だけさせる**——修正まで任せると、指摘の妥当性を自分で判断しないまま反映してしまう。

### 6つの観点

1. **要件が曖昧でないか**
   その記述だけを読んで実装を始められるか。「〜を管理する」「〜に対応する」で止まっていないか。
   *例：「レベルに応じて難度を変える」だけでは実装できない。何を測って、どの閾値で、超えたら何をするのかまで書けているか。*

2. **指標の測定方法が書いてあるか**
   目標値だけを書いて満足していないか。**誰が・いつ・どのデータで・どう計算するか**まであるか。
   *このプロジェクトでは [glossary.md](glossary.md) §5 が唯一の定義元。ここに無い指標を README に載せない。*

3. **ユーザーストーリーがあるか**
   その機能が**なぜ**必要かが書いてあるか。現状の何が困っていて、この機能でどう解決されるのか。
   *機能一覧だけのドキュメントは、後から「これは本当に要るのか」を判断できない。*

4. **非機能要件が検証可能か**
   数値目標に**測定環境・計測方法・判定基準**が付いているか。
   *「応答時間 2秒以内」は、どの環境で何回測った中央値なのかが無ければ検証できない。*

5. **用語が [glossary.md](glossary.md) と一致しているか** ←このプロジェクト固有
   同義語を作っていないか。コード上の識別子とドキュメントの用語がずれていないか。
   *ラベル体系がぶれると評価データが不整合になり、影響が最も大きい。*

6. **`docs/ja/` と `docs/en/` が揃っているか** ←このプロジェクト固有
   節・表・数値が両方に反映されているか。**ja を直して en を忘れていないか。**

### 見つかった問題の扱い

- **薄いままにする判断も正解。** 「実装が進んでから書く」と決めたなら、その旨をドキュメントに書き残す。**空欄のまま放置しない**（読み手には、忘れているのか意図的なのか区別がつかない）
- 指摘が実装の判断を含む場合（例：JSON が壊れたときの挙動）、**ドキュメントを直すだけで終わらせず、対応するタスクを `.steering/` の tasklist に足す**

## Git

- コミットメッセージは英語
- **コミットとプッシュは明示的に指示されたときのみ**
- `.env` は決してコミットしない
- ドキュメントは、それが説明する変更と同じコミットに含める。後からまとめて直さない

## セキュリティ

- 秘密情報は環境変数からのみ読む
- 入力長・録音長・1セッションのターン数・1日のトークンと音声合成の文字数に上限を設ける
- 学習者の音声と書き起こしは個人情報：保存前に同意を取り、氏名は保存せず、削除の手順を用意する
