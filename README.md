## 0. なぜこの題材か

**Junにしか用意できない資産が3つある。**

1. **評価データを自分で作れる**：日本語ネイティブなので正解データを自分で作れる。キャリアメモで埋めるべきギャップとして名指しされている「評価（evals）とドメインごとの基準づくり」が、外注も購入もせずに手に入る。**面接官は日本語が読めず出力の質を直接評価できないが、それは弱点であると同時に売りでもある**——「あなたが検証できないものを、私はネイティブとして検証できる。だから基準データを自分で作った」と言い切る。**この計画が「アプリの出来」ではなく「評価のやり方」を主役にしているのはそのため。**
2. **実ユーザーが近くにいる**：バンガロールには日本語学習者が実在する。**使われている数字（利用者数・継続率）**は、ポートフォリオで最も出しにくく最も効く指標。Deloitte の求人票の言葉でいう adoption（利用率）がそのまま出る。
3. **形態素解析（tokenization）が必然的に入る**：日本語は単語の区切りが空白で示されないため、機械処理には形態素解析が要る。**Cognizant の求人票が必須要件に挙げている「tokenization」を、こじつけでなく本当に必要だから使う形で示せる。**

**テスターの見込み（2026-07-28 確認）**：友人と Minna Shuugou（§2-5）で確保できる見通しが立ったため、**Cで進めることを確定**。8月末までに5人以上に触ってもらう。

## 1. 何を作るか

**バンガロールで日本語を学び始めた人が、AI と声で会話して、終わったあとに直してもらうアプリ。** 機能はこれだけ。

1. 場面を選ぶ（挨拶／自己紹介／お礼／簡単な依頼／予定と遅れの連絡／職場の敬語）
2. **「会話を始める」** → AI が先に話しかける（音声。**文字を出すかどうかは切り替えられる**——消すとそこで聞き取りの練習になる。既定は文字あり）
3. マイクを押して**声で話す** → AI が**声で返す** → また話す（**何往復でも**）
4. **「会話を終える」**
5. **振り返り**：話した文の一覧／直した方がよかったところ／自然な言い方／英語で短い理由

### 設計の芯（迷ったらここに戻る）

- **機能はこれ以上足さない。** 教材・ドリル・試験対策・単語帳・聞き取りクイズ・発音採点は作らない。既存サービスに機能の広さで勝てる見込みはなく、**評価されるのは機能の数ではない**。
- **入力は音声だけ。書かせない。** 日本語キーボードが要らず、アニメなどで耳から入った人がそのまま使える。タイピングは負担が大きく、話したい人の動機と合わない。
  - 聞き取れた文はそのまま画面に出し、**「もう一度」ボタン**を置く（打ち直させない）。押された回数は音声認識の質を測る目安になるので記録する。**自分の発話の文字は常に出す**（消すと言い直すかどうかの判断ができない）。切り替えられるのは **AI の返事の文字だけ**。
  - **マイクが使えない環境用の入力欄だけ隠しで残す**（機能として案内しない）。ミートアップで許可が下りない・雑音がひどい場合にテスターを失わないための保険。
- **絶対に外さないルール：学習者に自分の言葉で話させる。** 定型句をなぞらせる形にすると**直す対象が消え、訂正も評価も全部動かなくなる**＝このポートフォリオの中身がなくなる。易しくしてよいのは**場面**であって、話す中身を選択式にはしない。
- **場面は地続きに難しくなる**：挨拶 → お礼・依頼 → 予定や遅れの連絡 → 職場の敬語。**初級者は上まで登らなくてよい**。上があることで「日系企業で働く人まで使える」という広がりと、Jun 自身が日印の橋渡しで見てきた実体験が接続する。
- **発音の採点はしない。** 音声は入力手段であって、直すのは**言い方（自然かどうか）**。音素単位の評価やピッチアクセント判定は別領域で、手を出すと破綻する。学習者にもそう明示する。
- **Web アプリのみ。モバイルアプリは作らない**（理由は §2-2 末尾）。
- **画面と文書はすべて英語**。日本語が出るのは学習対象の文だけ。

### 見た目（和風・1時間で切る）

UI に機能は足さないが、**見た目にだけは1時間投資する**。README のスクリーンショットは面接官が最初に見るもので、**京都のような和の落ち着いた画面**は記憶に残り、題材とも一致する。機能を増やさずに印象だけ上げるのが狙い。

- CSS だけで足りる範囲：背景は生成り（#F7F4EC 前後）、文字は墨（#1C1C1C）、差し色は**藍か朱を1色だけ**。見出しは明朝系（Noto Serif JP 等）、余白を広く、罫線は細く、影は使わない。装飾を入れるなら1点だけ。
- **避ける**：鳥居・桜・忍者のイラスト、赤×金の派手な配色。**和風のクリシェは一瞬で安っぽく見える。** 引き算で作る。

### 既存サービスとの位置づけ

`japanesecompass.com` を調査：かな・文法・漢字・模擬試験・辞書・AI会話相手まで無料で揃った完成度の高いサービスが既にある。**機能の広さで戦えば必ず負けるので、機能では戦わない。**

差分は3つだけ。①**教材ではなく「話した文を直す」ことだけに絞る** ②**訂正の精度を数字で公開している**（既存サービスは精度を出していない＝**測っていること自体が差別化**）③**訂正の根拠を資料から引く**。

**README にこの比較を1段落書く。** 競合を調べたうえで戦う場所を選んだという説明は、Forward Deployed Engineer の面接で効く（顧客課題の翻訳と同じ筋肉）。

## 2. 設計

### 2-1. 中核＝訂正（薄いラッパーでない根拠）

大規模言語モデルに「この日本語を直して」と丸投げしない。**訂正を構造化して出させ、こちらで機械的に検証する。**

1. **会話ノード**：場面とレベルに応じて相手役の返答を生成（店員役・同僚役・上司役など）。**返事は1〜2文に短く保つ**（初級者に長文は届かないうえ応答時間も伸びる）。逐次出力 → 音声合成で読み上げ。**文字の表示は切り替え式**（消すと聞き取り練習になる。切り替えは表示だけで、裏の処理は変わらない）。**どちらで使ったかを記録しておく**と、9月以降に「慣れた人ほど文字を消して使うか」が見られる。
2. **訂正ノード**（会話とは別の呼び出し、①と並列）：学習者の発話について、以下を**構造化された形式**で出力させる。
   - **直した方がいいか（はい／いいえ）**
   - はいの場合：**自然な言い方**
   - **英語での短い理由**（1〜2文）
   - ※**誤りを種類分けしない**（助詞／活用…のような分類はしない）。初級者向けの会話には要らず、実装も評価も重くなるだけ。
3. **リファレンス検索（RAG）**：学習者の文を手がかりに文法の解説を検索し、理由の根拠として添える。根拠が引けない場合は断定しない。
4. **検証ノード（Python の確定処理）** ← ここが証明の核
   - **書き換えすぎの検出**：直した文と元の文の編集距離が閾値を超えたら「直し」ではなく「別の文」とみなして捨てる。
   - **語彙レベルの検査**：AI の返答を形態素解析にかけ、学習者レベルを超える語が閾値以上含まれていたら生成し直す。
   - **余計な直しの抑制**：根拠が引けておらず、かつ元の文が十分自然な場合は「直す必要なし」に倒す。

**この4番が「薄いラッパーでない」証明であり、§2-4 のベースライン比較で数字として効果を示す。**

**訂正は会話中に割り込ませない。** 1文ごとに直すと会話が途切れ、初級者は話す気をなくす。**訂正ノードは毎ターン裏で回しておき、結果は終了時にまとめて見せる**。会話が途切れず、「終える」ボタンにも意味が出る。

**マイクは Streamlit 標準の録音ウィジェット `st.audio_input` を使う**（公式ドキュメントで確認：WAV を返し、既定のサンプルレート16000Hz＝音声認識向けの品質。追加部品なしで録音できる）。

- **正確な操作（押して開始→もう一度押して停止なのか）と、スマホのブラウザで動くかは公式に記載がない。第1週に実機で確かめる**（§3 第1週）。ここが動かないと計画の前提が崩れるので、最初に潰す。
- **AI の返事の自動再生は `st.audio` の `autoplay` で可能**。ただし公式に「**ユーザーがページを一度もクリックしていないと自動再生されない**」という制約がある。今回は毎ターン録音ボタンを押すので条件を満たす（**最初の AI の挨拶だけは、開始ボタンを押した直後なので問題ない**）。

**ChatGPT の音声モードのような「押さずにずっと話す」形は8月にはやらない。** ただし理由は難易度ではない。

- エコー除去はブラウザ標準の機能で足り、**イヤホンを使えばそもそも問題にならない**。無音検知も静かな場所なら現実的（会話用のリアルタイム音声 API には組み込まれている）。**この2つは障害ではない。**
- 本当の壁は **Streamlit が常時つながった通信に向いていない**こと。操作のたびに画面のコードを実行し直す作りなので、音声を途切れず送り続けられない。外部の通信部品を足せば可能だが、無料のデプロイ先では接続が不安定になりやすい。
- 本気でやるなら **リアルタイム音声 API ＋ Streamlit 以外の画面**。送信・無音検知・割り込みは API 側が持ってくれるので実は楽になる。**引き換えに会話が LangChain / LangGraph を通る経路から外れる**（訂正側のパイプラインは会話後に回すので残せる。失うのは会話側だけ）。
- **8月に採らない理由は、Streamlit を捨てると作業時間が足りなくなるから**（お金ではない。API の利用料は画面を何で作っても変わらず月に数ドル）。画面が数行で書けることが56時間の見積りの前提になっており、録音・再生・状態管理・見た目を自前で書くと確実にはみ出す。
- **検討するのは11月の React 化の枠。** 8〜9月のテスターから「押すのが面倒」という声が実際に出たらやる。出なければやらない。**使った人の反応で決める。**

**テスターにはイヤホンを勧める**（エコーが消え、音声認識の精度も上がる）。

**形態素解析の役割**：日本語は単語が空白で区切られないため、「AI の返答に難しい語が混じっていないか」を機械的に見るには分かち書きが要る（文字列の一致だけでは語の境界が分からない）。**求人票の tokenization 要件はこの文脈でそのまま語れる。**

#### 評価は2段階に分けて測る（設計の要）

システムは「①声→文字（音声認識）」と「②文字→訂正」の2段。**通しの結果だけ見ると、どちらが悪いのか分からない。**

**音声認識は、学習者の言い間違いを勝手に直して書き起こすことがある。** そうなると訂正エンジンには最初から自然な文が届き、「直すところなし」と返す。学習者の間違いは指摘されないが、**訂正エンジン自体は何も間違っていない**（届いた文に対しては正しい判断）。通しの結果だけ見ると「訂正の精度が低い」という誤った結論になり、直す必要のない場所を直しに行くことになる。

| 測るもの | どう測るか | いつ |
|---|---|---|
| **②訂正エンジンの精度** | **アプリを通さない**。評価スクリプトが自作120件の**テキストを訂正エンジンに直接渡して**採点する。マイクも音声認識も経由しないので訂正の実力だけが出る（§2-4 の数字はすべてこれ）。**製品にテキスト入力を作る必要はない** | 8月 |
| **①音声認識の精度** | テスターの録音30件を**本人が聞いて「実際に何と言ったか」を書き起こし**、機械の書き起こしと比べる | 9月 |
| **通しの精度** | 同じ文を①経由と②直接の両方で流し、差を出す＝①がどれだけ誤りを消しているかが分かる | 9月 |

**①の正解データもネイティブにしか作れない**（インド人が話す日本語を聞き取って正解を書けるのは日本語話者だけ）＝§0 の武器が音声にもそのまま効く。**README には「訂正エンジンはテキストで測っている。音声段は別に測る」と明記する**——ここを曖昧にすると評価全体の信頼が落ちる。

**応答時間**も、音声段を含む時間と含まない時間を分けて載せる。

### 2-2. アーキテクチャ（8月末の完成形）

```
[Streamlit]  場面・レベルの選択／「会話を始める」「会話を終える」／録音ボタン／
             聞き取れた文＋「もう一度」／AI の返事（音声＋文字）／終了後の振り返り／和風の配色
      │ HTTP（REST）／アクセスコードで保護
      ▼
[FastAPI]  POST /chat   POST /check   GET /health
      │  ＋ 1セッションのターン上限・1日のトークンと音声合成の上限
      ▼
[LangGraph]
   ① 会話ノード（LangChain → Claude API、逐次出力、1〜2文）→ 音声合成で読み上げ
   ② 訂正ノード（構造化出力）※①と並列。会話中は出さず、終了時にまとめて表示
   ③ リファレンス検索ノード（Chroma ← 文法解説を多言語埋め込みで検索）
   ④ 道具：形態素解析（SudachiPy）＝語彙レベルの判定
   ⑤ 検証ノード（§2-1 の4。Python の確定処理。落ちたら②へ差し戻し1回まで）
      ▼
[PostgreSQL（無料枠）]  同意記録・利用ログ（発話・訂正結果・レイテンシ・トークン）
      ▼
[評価スクリプト]  自作120件を訂正エンジンに直接流して測定 → 数字を README へ
```

- **8月前半は縦スライス**：まず Streamlit 直結・テキストで会話と訂正を動かして中身を固め、**そのあと**音声に載せ替え、FastAPI と LangGraph へ切り出す。
- モジュール分割：`dialogue/` `correction/` `retrieval/` `nlp/` `evals/` `app/`。
- **画面は1つだけ**：同じ画面が「会話中」と「振り返り」で切り替わるだけにする（別ページを作らない）。指標は README に載せるので画面には出さない。**画面を増やす提案が出たら断る。**

**なぜ Web アプリだけにするか（モバイルアプリを作らない理由）**

- **審査と手間が丸ごと無駄**：Apple Developer Program は年99ドル＋審査があり、Mac と Xcode が要り、配布に TestFlight を挟む。この工数はすべて求人要件と無関係。
- **テスターが減る**：Cの最大の武器は実ユーザーの数字。**インストールを挟んだ瞬間に触ってくれる人は激減する。** URL を送るだけが最も摩擦が小さい。
- **面接官も触れない**：README のリンクをその場で開けるのが Web の強み。
- **求人票にモバイルの要件がない**：求められているのは FastAPI・Docker・RAG・LangGraph・評価。
- **ただしスマホで開かれる前提は必要**：テスターは携帯で開く。作り込みはしないが、**配る前に一度スマホで開いて、会話と振り返りが読めるかだけ確認する**（5分）。

**踏みやすい落とし穴**：無料のデプロイ先（Streamlit Community Cloud、Hugging Face Spaces）は**ファイルが再起動後も残ることを公式に保証していない**（公式ドキュメントに記載を確認できなかった＝当てにできない）。利用ログをファイル保存にすると、テスターの数字を失う可能性がある。**最初から外部のデータベース（Neon か Supabase の無料 PostgreSQL）に書く**こと。設定は30分程度で、「保存先を意識して設計した」という信号にもなる。

### 2-3. データ

1. **評価用データ（自作＝Cの最大の資産）**
   - **8月は120件**（9月に250件へ）。内訳＝**直した方がいい文90件**＋**そのままで自然な文30件**（余計な直しを測るため）。**初級者が言いそうな文にする**（挨拶・自己紹介・お礼・簡単な依頼あたり）。
   - **誤りの種類は付けない。** 「直した方がいいか／そのままでいいか」の2択と、直した文だけあればよい。
   - 各件の項目：`id` / `場面` / `学習者の文` / `直した方がいいか（OK か NG）` / `自然な言い方（NG のみ）` / `理由の要点（英語）` / `分割（dev か test）`。
   - **作り方＝大規模言語モデルに候補を出させ、本人が全件を検証・修正する。** ゼロから手書きしない。**この作り方自体が語れる**：「候補生成は自動化し、ネイティブとして全件を検品した。だから規模を増やせる」＝評価データ作成の方法論として正しい。
   - 出どころ＝日本語学習者の典型的な言い間違い。**特定個人の発言をそのまま使わない**（一般化した文にする）。
   - リポジトリに JSON で入れる。**これ自体が公開成果物**になる。
2. **文法リファレンス（自作。RAG の検索対象）**
   - **8月は10本**（9月に25本へ）。1本200〜400語。助詞の使い分け、です・ます、自己紹介の型、お礼と依頼の型、丁寧さの段階など。
   - **1つの話題に複数本が当たるように書く**（1話題1本だと検索が単なる対応表になり、「RAG と呼べるのか」と突っ込まれる）。
   - 自作なので著作権の問題なし。
3. **形態素解析器と辞書（公開データ）**
   - **SudachiPy ＋ SudachiDict**（分かち書き・語の正規化・頻度による難易度判定）。**両方とも Apache-2.0 で継承条件なし＝同梱の心配は不要**（確認済み）。README に出典と license を明記するだけでよい。
   - **辞書は別の pip パッケージ**で、標準版で約70MB。**Docker のイメージが膨らむ**ので、ビルド時に入れる前提で書く。
   - JMdict / KANJIDIC2 は継承条件（CC BY-SA）があるため、使うなら同梱せず取得スクリプトにする（現時点では使わない）。
   - **市販教科書と日本語能力試験の過去問は取り込まない。** 難易度の区分は語の頻度から自作し、「日本語能力試験の水準におおよそ対応」という表現に留める。

### 2-4. 評価の設計（Cの主役）

**開発用と評価用を分ける。** 120件を **開発用80件 / 評価用40件** に固定し、プロンプトや閾値の調整は開発用だけを見て行う。評価用は最初と最後にしか触らない。**これをやらないと「自分で調整したデータで自分を測った数字」になり、評価として無価値。** README に分割方針を1行書くだけで、評価を分かっている人だと伝わる。

**ベースラインを先に測る。** 実装の最初に、**素朴版**（大規模言語モデルに「この日本語を直して、理由を教えて」と1回投げるだけ）を作って評価用データで測る。そのうえで本実装（検証ノード・形態素解析・RAG つき）を測り、**同じ表に並べる**。

| | 素朴版（1回呼び出し） | 本実装 |
|---|---|---|
| 判定の正しさ | | |
| **余計な直しの率** | | ← ここが一番差が出るはず |
| 直しと理由の妥当性 | | |
| 応答時間（95パーセンタイル） | | |
| 1ターンあたりのコスト | | |

**この表がプランCで最も強い1枚。** 「AIに投げただけではないのか」という質問に、数字1つで答えられる状態になる。

**指標の定義（曖昧さを残さない）**

| 指標 | 定義 | 8月の目標 |
|---|---|---|
| 判定の正しさ | 直した方がいい文90件のうち、「直した方がいい」と判定できた割合 | 85%以上 |
| **余計な直しの率** | そのままで自然な文30件のうち、誤って直した割合（低いほど良い） | 15%以下 |
| 直しと理由の妥当性 | 40件を本人が3段階（妥当／不十分／誤り）で採点。採点基準を README に明記。**うち20件は別の日本語ネイティブにも採点してもらい一致率を出す** | 妥当85%以上／一致率80%以上 |
| 検索の当たり率 | 学習者の文に対して、根拠として妥当な解説が上位3件に入った割合 | 80%以上 |
| レベル遵守率 | AI の返答に、指定レベルを超える語が閾値以上含まれなかった割合 | 90%以上 |
| 応答時間 | 中央値・95パーセンタイル（音声段の有無で分ける） | 改善前後を比較 |
| 利用 | テスター人数、1人あたりの会話ターン数 | 5人以上 |

**参考にした失敗例（llm-jp-eval）**

日本語の大規模言語モデル評価には **llm-jp-eval**（国立情報学研究所系の LLM-jp と Hugging Face による標準的なベンチマーク集、16タスク）と **Open Japanese LLM Leaderboard** がある。**誤り訂正のタスクが入っていない**のでそのまま流用はしないが、2つの使い道がある。

- **自作ベンチマークの存在理由になる**：「日本語の標準ベンチマーク集には文法誤り訂正のタスクがない。だから自分の領域向けに作った」と README に1行書く。
- **失敗例のカタログとして使う**：Hugging Face の批判記事（`leonardlin/llm-jp-eval-eval`）が指摘する問題は、**そのまま自分の評価で踏む罠**。

| 批判記事が指摘した問題 | 自分の評価で同じことが起きる場所 | 対策 |
|---|---|---|
| **完全一致採点が脆い** | 直した文の照合。自然な言い方は1つに決まらないので、正解と1文字違うだけで不正解にすると実力より低く出る | **直した文は完全一致で採点しない**。判定（OK か NG か）だけ機械採点し、直し方の良し悪しは本人＋第二採点者の目視で見る |
| **言語の取り違え** | 理由は英語で出させる設計なので、日本語で返ると中身が正しくても減点される | **書式適合率**を別に測る（英語で返ったか・JSON が壊れていないか）。中身の精度と混ぜない |
| **プロンプトの書式で点数が動く** | プロンプトを直すたびに数字が動き、改善か偶然か分からなくなる | **実行記録**を残す：測定ごとにモデル名・プロンプトの版・日付・データ分割を JSON に保存し、README の数字にどの版かを書く |
| **採点スクリプトの不具合に気づかない** | 数字が良すぎる／悪すぎる時に切り分けられない | 評価用データから**5件を手で照合**する工程を毎回入れる |

**この内容を README に短く書けると強い。** 「評価を作った」ではなく「**評価が壊れる典型例を知ったうえで作った**」に格が上がり、Cognizant や Deloitte の求人票にある evaluation frameworks の要件に、言葉ではなく中身で当たる。

- **第二の採点者を必ず入れる**：「直しと理由の妥当性」だけは自動採点できず本人の主観が入るため、**自分が作ったシステムを自分だけで採点した数字は最も弱い**。20件でいいので別の日本語ネイティブに同じ基準で採点してもらい、**一致率**を併記する（Minna Shuugou に日本人参加者がいる）。所要は相手の30分程度。
- **信頼区間を併記する**：評価用40件では誤差が±8ポイント程度ある。「92%（n=40、目安の誤差 ±8pt）」と書く。**数字を大きく見せず、限界を自分から書けることが信頼を得る。** 目標に届かなくても、届かなかったことと理由を書けば減点にならない。
- **改善サイクルを1周は必ず回して README に書く**（例：余計な直しが多かったので、根拠が引けない時は直さない規則を足したら 28% → 12%）。**何を直したら数字がどう動いたかが8月の成果物の中核。**

### 2-5. 実ユーザー（Cの武器）

- **8月末までに5人以上**（9月末に20人）。
- **募集は第1週から**（第3週に配ってから探すのでは間に合わない）。**前向きな返事が3人未満なら第2週の頭で計画を見直す。**
- **本命は Minna Shuugou**（バンガロールの日本文化コミュニティ、参加経験あり、WhatsApp で連絡）。**開催日を先に確認し、第3週に間に合う回を押さえる。** ほかに INDIGITAL の同僚、GDG Bangalore。
- **日本人参加者には第二の採点者を頼む**（§2-4）。テスターにならなくても、20件の採点で評価の信頼性が上がる。
- **テスター1人ずつに別のアクセスコードを配る**（共有コードにしない）。**誰が何回来たかが分かる＝継続率が測れる**。アカウント登録は作らない。あわせて1セッションのターン上限と1日の利用上限を入れる。
- **同意と注意書き**：録音が外部の API に送られること、改善のために保存すること、**機密情報や個人情報を話さないこと**、**AI の声は合成音声であること**（音声合成の利用規約が明示を求めている）、削除依頼の連絡先。同意した人のみ保存。氏名は保存しない。**音声そのものは9月の書き起こし比較に使う分だけ残す。**
- **会社の時間・資金・データ・機材は使わない。** 同僚に見せるときも**個人プロジェクトだと明示**する。
- **収益化はしない**（就労ビザが INDIGILAB に紐づいており、インド国内で収入を得るのはビザ違反の恐れがある）。指標は利用と継続で取る。

## 4. 実行計画（2026年9月〜）

**8月で「動くものと数字」は揃う。9〜11月は「本番で通用する厚み」を足す3か月。12月から応募を始める。**

朝2時間は継続。9〜11月は月あたり **35〜40時間**（8月より落として持続させる）。

### 9月 — 実ユーザーの数字と、音声段の精度

**目的**：8月の「5人が触った」を「20人が使い、続けている」に変える。あわせて音声段の精度を出し、評価の空白を埋める。

| 週 | やること |
|---|---|
| 1 | 復習しやすいように**テスターを20人へ拡大**（Minna Shuugou の9月の回＋GDG＋同僚の紹介）。アクセスコードを配る運用を回す |
| 2 | **録音30件を本人が聞いて書き起こす**（1件2〜3分＝2時間程度）。機械の書き起こしと比べ、**文字単位の誤り率**を出す |
| 3 | **同じ文を音声経由と直接の両方で流し、訂正の判定がどれだけ変わるかを測る**（＝音声段が学習者の誤りをどれだけ消しているか）。README に §2-1 の表の数字を埋める |
| 4 | 実際の録音から**評価データを250件へ**（実ユーザーの言い間違いが最良の材料）。**改善サイクル2周目**（一番低い指標を1つ直す） |

**月末に言えるようになること**：「20人が使い、週次継続率は○%。音声認識の誤り率は○%で、そのうち学習者の誤りを消してしまう割合は○%だと分かったので、評価は2段階に分けて報告している。」

**落とすなら**：評価データ250件（180件でもよい）。**録音の書き起こしは落とさない**——ネイティブにしか作れない資産で、Pixie Dust の経歴と直結する。

### 10月 — 観測（MLOps の入口）と、人手評価の自動化

**目的**：Wipro などが求める **MLOps** の語彙を埋め、評価の一番弱い部分（本人の主観採点）を自動化する。

| 週 | やること |
|---|---|
| 1 | **リクエスト単位のログ**（レイテンシ・トークン・費用・音声段の失敗・「もう一度」の回数）を構造化して保存 |
| 2 | **簡単なダッシュボード**（Streamlit の別タブでよい）。日次の利用・失敗率・平均応答時間・1会話あたりの費用 |
| 3 | **直しと理由の妥当性を別モデルで自動採点し、本人の採点との一致率を測る**。一致率が高ければ以降は自動採点で回せる＝**人手評価を自動化する方法論**が語れる |
| 4 | **復習リストの画面**（保存した訂正を見返す＝再訪の動機）。**改善サイクル3周目** |

**月末に言えるようになること**：「利用のログを取り、費用と失敗を日次で見ている。人手でしか測れなかった評価項目は、別モデルの採点が人と○%一致することを確認したうえで自動化した。」
