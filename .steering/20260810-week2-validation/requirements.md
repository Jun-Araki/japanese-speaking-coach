## 今回やること

**「AI に投げただけではないのか」に数字で答えられる状態にする。**

第1週で出したのは**素朴版の数字だけ**で、比較する相手がいない。今週やるのは3つ。

1. **検証ノード**（Python の確定処理）と**形態素解析**を入れ、素朴版との差を作る
2. **文法リファレンスを検索して根拠を引く**（RAG）。検索単体の当たり率も測る
3. **ベースラインと本実装を同じ分割・同じ日に測り、比較表を README に置く**

音声・FastAPI・LangGraph・PostgreSQL・Docker・テスターへの配布は**すべて今回の範囲外**。

## なぜこの範囲か

- **比較表は8月の成果物の中核**であり、PLAN.md は 8/16 を「ここが出ていれば以降どこで遅れても価値はゼロにならない」最低ラインに置いている。**今週の全作業はこの1枚に向けて並べる。**
- **検証ノードは「薄いラッパーでない」ことの唯一の証明**（PLAN.md §2-1 の4）。
- **RAG を今週に入れるのは、根拠を示すこと自体が DoD だから**。あわせて、余計な直しの抑制（検証③）が「根拠が引けたか」に依存する。
- 音声を今週に載せない理由は第1週と同じ。**中身が固まる前に載せると、悪いときに音声のせいか訂正のせいか切り分けられない。**

## ユーザーストーリー

1. **学習者として**、AI の返事に自分のレベルを超える単語が並ばないので、聞き返さずに会話を続けられる。
2. **学習者として**、直された理由に文法の根拠が付いてくるので、その場限りの指摘ではなく次に活かせる。
3. **学習者として**、もともと自然だった自分の文を直されないので、「何を言っても直される」という無力感を持たずに済む。
4. **開発者（Jun）として**、素朴版と本実装を同じ分割・同じ日に測った表が見られるので、検証ノードに意味があったかを判断できる。
5. **面接官として**、README の比較表と `n` と誤差を読むだけで、この人が評価を分かっているかが判断できる。

## 制約事項

- **`test` に触るのは 8/11 の測定1回だけ。** 誤り分析も改善サイクルも `dev` で行う
- **8/10 の裁定より後、`test` の項目を1件も変更しない**（`items_digest` が動く）
- **`test` の実行では per-item を一切出さない**（記録にもコンソールにも）。
  **採点スクリプトの検査は、同じ枠の中で `dev` を数件回して行う**
  ——現状の `_print_manual_check` は `split` を見ずに正解と判定を印字する。
  **「読んでも使わない」という規律で守らない。仕組みで閉じる**（第1週の教訓）
- **8/11 の測定より後に `scorer_version` を上げない。** 指標の**追加**は既存2指標の計算を変えない限り許す。
  **変わっていないことを pytest で固定する**（規則を4回書いても、確かめる手段が無ければ守られない）
- **ベースラインは今週1文字も変えない**
- **`correction/` から `politeness_rule()` と `POLITENESS_ADJUDICATIONS` を import しない。**
  これらは**評価項目（eval-081 は `test`・eval-017・eval-022）を実例として引用している**ので、
  訂正エンジンに入れると **`test` の正解を手で埋め込んだことになる**。pytest で縛る
- **`[retrieval] score_min` を、比較表の指標（`detection_accuracy` / `over_correction_rate`）を見て決めない。**
  この閾値は③の発火を通じて両指標を直接動かす。**決定基準は検索単体の性質**にする（design.md）
- **閾値をコードに直値で書かない**（`config/thresholds.toml` から読む）
- **`data/grammar/` は評価データを引用しない。** 照合は**句読点を落として**行う
- **`level_compliance_rate` の台本に評価データを使わない**（`test` を会話生成に通さない）
- **誤りの種類分けはしない**（glossary §2）
- **`docs/ja/` を先に直し、`docs/en/` を同じコミットに含める。README も3面目のドキュメントである**
- 秘密情報は環境変数。`.env` はコミットしない
