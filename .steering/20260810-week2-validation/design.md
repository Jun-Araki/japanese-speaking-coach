## 実装アプローチ

**今週も素直な関数呼び出しで書く。LangGraph には載せない。**

```
Streamlit (app/)
   │
   ├──▶ dialogue.reply(scene, level, history) ──▶ LLM ──▶ 1〜2文
   │        └──▶ nlp.level_check(reply, level) ──── 超過 ──▶ 1回だけ再生成   ← 検証②
   │
   └──▶ correction.check(sentence, scene, level)
              │  retrieval.search(sentence) ──▶ Chroma ──▶ score_min 以上を grounding_ids
              │  LLM（構造化出力）
              └──▶ correction.validate(original, result, grounding_ids)   ← 後処理
                        ├ 検証① 書き換えすぎ  → 訂正を捨て false で返す（discarded を記録）
                        ├ 検証③ 根拠なし＋自然 → false へ倒す（採否は事前登録した基準で判定）
                        └ 通過                  → そのまま
```

**検証は「生成のあとに走る Python」であって、2回目の生成ではない。** モデルに
「これは直しすぎですか」と聞く形にすると、**検証ノードは検証ではなくなる**——同じ確率的な
判断をもう一度引いているだけで、素朴版との差が「呼び出し回数」に化ける。

**そして、後処理であることには測定上の利点がある。** 検証は LLM の出力に対する確定処理なので、
**同じ出力に対して「検証を当てた場合」と「当てなかった場合」を、追加の API 呼び出しゼロで両方作れる。**
段を分けた測定（下記）が安く済むのはこのためで、**しかも段の差にサンプリングの揺れが混ざらない。**

### 段は4つに割る（1回で全部入れると、何が効いたか1つも言えない）

今週の3本柱は「プロンプト」「RAG」「検証」の3つで、**素直に1回測ると3つの差が1つの数字に潰れる。**

| 段 | 中身 | 直前の段との差が意味するもの |
|---|---|---|
| ベースライン | 素朴な1回呼び出し | — |
| **⓪** | 本実装のプロンプト・RAG なし・検証なし | **プロンプトの差** |
| **①** | ＋RAG | **RAG の効果** ← これが無いと、今週の3本柱の2つ目について比較表が何も言わない |
| **②** | ＋検証①（書き換えすぎ） | 検証①の効果 |
| **③** | ＋検証③（余計な直しの抑制） | 検証③の効果 |

**②③は①の出力に後処理を当てるだけなので、追加の API 呼び出しは要らない。**
**しかも①と②の差は検証器だけで、サンプリングの揺れが1ミリも混ざらない。**

**検証②（レベル超過）はこの梯子に載らない。** `dialogue.reply()` の中で起き、
評価スクリプトは `correction.check()` しか呼ばないからである（PLAN.md §2-1「訂正はアプリを迂回して測る」）。
**②の効果は90返答の測定側で見る**——訂正の実行記録に `validation_fired` を置くと、
**②は構造上つねに 0 になる。**

### `test` の実行では per-item を一切出さない

第1週 Day 7 の伏せ字化は実行記録だけを塞いだが、**コンソール出力が塞がっていなかった。**
`evals/score.py` の `_print_manual_check` は **`split` を見ずに**、正解ラベル・システムの判定・
システムの直しと理由・自分の正解を印字する。8/11 に走らせると
**`test` 40件のうち5件（12.5%）の当たり外れが確定的に分かる。**
`over_correction_rate` の分母は13件なので、**分母の8〜15%について結果を見たうえで
1週間 `dev` を調整する**ことになる。

**「学習者文とシステムの直しだけ出す」では足りない。** 手照合の目的は
コード自身が書いているとおり「**採点スクリプトの不具合と、モデルの不出来を切り分ける**」ことで、
切り分けに要るのは `expected` と `predicted` の突き合わせ——**まさに伏せたいもの**である。
残るのはモデルの検査であって採点器の検査ではない。

**したがって、目的のほうを別の場所へ移す。**

1. **`test` の実行では per-item を1行も出さない**（記録にもコンソールにも）
2. **同じ枠の中で、`test` の測定の直前に `dev` を数件、同一 `scorer_version` で回して手照合する。**
   `dev` なら何を見てもよい。**採点器の検査はここで完結する**
3. 実行記録に `scorer_checked_on`（その `dev` 実行の `run_id`）を残す

**「伏せつつ採点バグを検査する」は `test` 上では両立しない**——`items.json` は
`needs_correction` を全件公開しているので、id と判定を並べれば当たり外れの表示と同値になる
（第1週 Day 7 の `japanese_left_unquoted` と同じ論理）。**両立しないものを両立させようとしない。**

### `retrieval_hit_rate` は、測り方を先に決めないと必ず高く出る

glossary §5 の定義は「学習者の文に対し、根拠として妥当な解説が上位3件に入った割合」だが、
**どの件で測るか・誰が妥当性を決めるか・いつ決めるかが書かれていない。**
**検索結果を見てから「まあ妥当だ」と判定すると、当たり率はほぼ100%になる。**

**順番を固定する。**

1. **`dev` から30件を選ぶ。** 下記の一致件を機械で除外してから選び、**内訳を先に固定する（`true` 20 / `false` 10）**
   ——`false` を入れないと、**検証③が依存する「このままでよい側の根拠が引けるか」が一度も測られない**
2. **各件に「根拠になるべきリファレンス id」を手で付ける**（検索は回さない）
3. **30件を10件（閾値決定用）と20件（測定用）に分ける**
4. **10件で `score_min` を決め、20件で `retrieval_hit_rate` を測る**（`n=20` と書く）

### `[retrieval] score_min` は、比較表の指標を見て決めない

**この閾値は「検出率と過剰訂正率のどちらを良く見せるか」のつまみになりうる。**
③の発火は「`grounding_ids` が空」に依存し、`grounding_ids` は `score_min` が決めるからである。

- `score_min` **低** → 根拠がほぼ常に付く → ③が発火しない
- `score_min` **高** → 根拠が空になりやすい → ③が広く発火し、両指標が動く

**「決めた回の `retrieval_hit_rate` は公表しない」では守れない。**
`retrieval_hit_rate` は**順位の指標で、採否の下限である `score_min` に対して不変**である。
**守るべきは `over_correction_rate` と `detection_accuracy` のほうで、そこに防護が無かった。**

**決定基準を検索単体の性質にする**：**上の10件について、手で付けた正解 id が
`score_min` 以上で残る割合（再現率）**で決める。これは比較表の指標と独立している。
**値と、それを決めたデータと量を `thresholds.toml` にコメントで残す**（既存3つと同じ書式）。

| 分割 | 学習者文または直した文がそのまま残っている件 |
|---|---|
| **`dev`** | **16件**（うち `true` 12 / `false` 4） |
| `test` | 8件（grammar-008 に7件、grammar-004 と grammar-007 に各1件） |

- **走査対象は `data/grammar/` 全体 × 120件全体。** grammar-008 だけを想定して書くと**残り2本を通したまま緑になる**
- 見るのは `learner_sentence` / `corrected_sentence` / `reason_en` の3つ
- **`test` の一致はハード失敗。`dev` の一致は「整数の件数」ではなく `id` の許可リストで固定する**
  ——整数だと、リファレンスを増やして新しい一致が出たとき**数字を1つ増やせば緑に戻り、diff は1文字しか出ない。**
  id の許可リストなら追加が1行の diff として見え、そこに理由を書ける。
  **`test` 由来の id は許可リストに入れられないことをテスト側で強制する**
- **照合は `。、？！「」` を落としてから**（第1週に `はじめまして` と `はじめまして。` が素通りした）

**`dev` の一致件は 30件の母集団から除外する。** 除外の向きは**保守側**である
（文字列が一致している件は当てやすいので、除くと当たり率は**下がる**）。ただし
**除外した16件は定型句に集中している**ので、**当たり率はその話題について何も言わなくなる。**
README に1行書く。

**`test` の引用を差し替えるとき、差し替え先は `dev` の現象から採るか、評価データを見ずに書く。**
「同じ現象をなお説明できるように」`test` を見ながら選ぶと、**検索コーパスを `test` に合わせて整形した**ことになる。

**「近似一致」は関数で定義するか、諦める。** 第1週の「約30件」は目視の見積りで再現できない。
定義を書けるなら書き（例：句読点除去後の文字 3-gram Jaccard ≥ 0.6）、
**書けないなら別集計は完全一致の除外だけにして、README にそう書く。**
実体が目視のまま「近似も別に集計している」と書けば、**それは測っていない数字を測ったことにする。**

### 掃除で「このままでよい」の根拠を減らさない

第1週の監査2周目は「リファレンスが『これは誤り』の説明ばかりで、**『この文はこのままでよい』の
根拠が1つも無かった**」として6箇所を足した（grammar-002・003・005・006・007・008）。
その1つが grammar-007 の**「少し考えます」は上司にもこのままでよい**＝**eval-060（`test`）の学習者文**で、
**ハード失敗の対象なので必ず消える。**

**本数を数えるだけでは足りない。** 別の文に替えて本数を保っても、扱う現象が変われば③の根拠にならない。
**掃除の前後で「どの現象を扱っているか」を1語ずつ書き添えて比較する。**

### `level_compliance_rate` は、ゲートと同じ関数で測ると自動的に達成される

検証②は**同じ `level_check()` で不合格になった返答を再生成する**。したがって②を入れたあとの値は
`1 −（2回連続で不合格になる確率）` に収束し、**返答が実際に初級者に分かるかとは無関係に90%を超える。**
**第1週が制約デコードを避けた理由と同じ罠**（`format_compliance_rate` の JSON 側が構造上つねに100%になる）。

**対処：2つの値を分けて出す。**

| 値 | 意味 | 目標 |
|---|---|---|
| **1発目の遵守率** | **ゲートに頼らない素の品質**。README の主値 | 掛けない（参考値） |
| 再生成後の遵守率 | 運用上の値 | **PLAN.md §2-4 の 90% はこちらに掛ける** |

**README に「再生成後の値は同じ関数でゲートした結果なので、独立の証拠ではない」と併記する。**
決めずに測ると、第4週に「どちらで達成したか」が争点になる。

**測り方**：6場面 × 5ターン ＝ **30往復の固定台本**を書き、3レベルで流して **90返答**。
**台本は評価データを一切使わず新規に書く**（`SCENE_BRIEFS` の開始文から自然に続く形）——
`items.json` から採ると `test` の文を会話生成に通すことになる。
`dialogue.reply()` は `temperature = 0.7` なので**返答は固定されない**。
**今週は1試行とし、README に「n=90、1試行、temperature 0.7」と書く**（3回引く余裕が枠に無い）。

## 検証ノードの設計

### 捨てた訂正を、どう返すかを先に決める

**①が「訂正を捨てる」と書いてあるだけでは、`check()` が何を返すかが決まらない。**
`needs_correction: true` のまま返すと `score.py` は加点したままになり、
**学習者には何も表示されないのに検出率だけ高い本実装**が README に載る。
しかも `corrected_sentence` が空の `true` は `parse_correction` が禁じている形である。

**捨てたら `needs_correction: false` として返し、`discarded` を実行記録に残す。**

> **`delivered_detection_accuracy` は足さない。** `false` で返すと決めた時点で、
> 「`predicted` が `true` の件」と「訂正が届いた件」は**同じ集合**になり、
> **2つの指標は恒等的に一致する。** README に同一の2列が並ぶだけになる。
> **同じ情報は段を分けた測定（①→②）が持っている**ので、指標を足すのではなく段で見る。

### 検証③の述語は、実測してから採否を決める（事前登録）

規則は「**根拠が引けておらず、かつ元の文が十分自然なら『直す必要なし』に倒す**」（PLAN.md §2-1）。
問題は「十分自然」を何で判定するかで、**素直に書くと `test` の正解をエンジンに埋め込む。**

`dialogue/scenes.py` の `politeness_floor()` は **述語ではなく `(段階, 英語の説明)` のタプル**である。
忠実に述語化しようとすると例外規則が要り、その例外は `POLITENESS_ADJUDICATIONS` にあって、
**`お仕事、何？`（eval-081・`test`）と `はじめまして`（eval-017 の正解）と
`お名前は。`（eval-022 の正解）を実例として名指ししている。**
**入れれば、第4週の `test` 再測定は eval-081 を「eval-081 から作った規則」で答えることになる。**

**そこで、評価項目に由来しない機械判定に置き換えた。ところが当ててみたら判別力が無かった。**

**2026-08-10 の実測**（120件の学習者文の文末を判定）。

| 述語 | `false` 30件（守るべき側） | `true` 90件（止めてはいけない側） | 差 |
|---|---|---|---|
| **文末が `です/ます/ください/でしょうか`** | **30.0%** | **37.8%** | **−7.8pt（向きが逆）** |
| 丁寧助動詞まで広げる（`ました/ますか` 等） | 73.3% | 66.7% | +6.6pt |
| **場面の段階を見る版**（下記） | **93.3%** | **81.1%** | **+12.2pt** |

**素朴な形は乱数より悪い。** 原因は**場面の段階を無視したこと**である
——glossary §2 は丁寧さの下限を**相手で決まる3段階**とし、**段階A（`greeting` / `thanks`）は
丁寧形を要求しない**。そこに丁寧形の有無を当てれば、くだけた形が正解の場面で
**11件の `false` のうち10件が「自然でない」と判定される。** 段階Aは
**モデルが丁寧形へ直したくなる筆頭**であり、③が最も効くべき場所そのものである。

**採る形**：**段階A の場面は無条件に通し、段階B・C だけ文末を見る。**
段階は `POLITENESS_FLOORS` のタプルの**第1要素だけ**を使う——**段階は場面のメタデータであって、
評価項目を1つも引用していない。** `politeness_rule()` と `POLITENESS_ADJUDICATIONS` は使わない。

**それでも +12.2pt しかない。** ③は3つの条件の**論理積**（根拠が空・編集距離が小さい・この述語）なので、
判別の主力は「根拠が空」でなければならず、**この述語を主力として説明しない。**

**したがって採否を事前登録する。**

- **基準**：`dev` で **`false` 側の発火率が `true` 側より 20pt 以上高いこと**
- **満たさなければ採用しない。** そのときは**測定結果を README に書く**
  ——「実装できなかった」ではなく「**当てたら判別力が無かった**」と書ける
- **判定は追加の API 呼び出しゼロでできる**（①の出力に後処理を当てるだけ）
- **`validation_fired` は `true` / `false` 別に数える。** 合計だけだと、この判定ができない
- **基準を先に書いてから測る。** 結果を見てから基準を決めれば、それは基準ではない

**`correction/` から `politeness_rule()` と `POLITENESS_ADJUDICATIONS` を import したら落ちる pytest** を置く。
`politeness_floor` と `politeness_rule` は**1文字違い**で、第1週は `generate_items.py` についてしか縛っていない。

### 閾値の確定手順

**`dev` の `needs_correction: true` 件に訂正を流し、この閾値で捨てられる件を数える。
正しい訂正が1件でも捨てられたら閾値を上げる**（`thresholds.toml` の TODO）。

> **8/13 に流すのはベースラインの訂正である。** 閾値が実際に掛かるのは本実装の訂正で、
> そちらは根拠つき・別プロンプト・再試行ありなので**編集距離の分布が違う。**

**①は「正しい訂正が1件でも捨てられたら閾値を上げる」規則で確定するので、発火0件に収束するのが
最も安全な着地になる。** 発火0件のノードがあれば、README に

## Day 3：計画の前提が1つ崩れた —— SudachiDict は頻度を持っていない（2026-08-11）

`config/thresholds.toml` は `[vocabulary_level]` に
**「Tokenised with SudachiPy; frequency tiers come from SudachiDict」**と書き、
PLAN.md §2-3 も **「SudachiPy ＋ SudachiDict（分かち書き・語の正規化・頻度による難易度判定）」**
としている。**実物を当たったら、頻度は取れなかった。**

`Morpheme` が公開しているのは `surface` / `normalized_form` / `dictionary_form` /
`reading_form` / `part_of_speech` / `word_id` / `is_oov` / `split` / `synonym_group_ids` だけで、
**コストも頻度も無い。** `get_word_info()` は残っているが**非推奨**（"Users should not touch the raw
WordInfo"）で、`WordInfo` にも頻度は入っていない。配布されているのはコンパイル済みの辞書で、
**頻度を持つ元の CSV は同梱されていない。**

**分かち書きと正規化は予定どおり動く**（`nlp/tokenize.py`、pytest 7件）。
**崩れたのは「段階をどこから取るか」だけである。**

> **ここで代わりの段階を黙って発明しない。** `level_compliance_rate` は glossary §5 に定義があり
> README の目標表にも載っている**公開する指標**なので、**出どころを変えるなら定義のほうを直す。**
> 「頻度による」と書いたまま別のもので測れば、**測っていないものを測ったことにする**——
> 第1週に制約デコードを避けた理由と同じ。

### 頻度リストを外から入れる（2026-08-11 決定）と、その裏取り

**Jun の判断：公開の頻度リストを取り込む。** PLAN.md §2-3 の「頻度による難易度判定」と
glossary §5 の定義を**書き換えずに実装できる**のはこの道だけである。

**候補を2つ当たり、ライセンスで結論が出た。**

| 候補 | ライセンス | 判定 |
|---|---|---|
| **BCCWJ 短単位語彙表**（国立国語研究所） | 「**研究・教育目的での利用は無償**」。**再配布の可否は明示されていない** | **採用。ただしリポジトリに同梱しない** |
| `wordfreq`（PyPI） | コードは Apache-2.0 だが、**データは CC BY-SA 4.0** | **不採用** |

**`wordfreq` を落とした理由は2つあり、どちらも具体的である。**

1. **データが CC BY-SA 4.0 ＝ 継承条件つき。** PLAN.md §2-3 が JMdict / KANJIDIC2 を
   **同じ理由で外している**ので、ここだけ通すと基準が二重になる
2. **日本語の分かち書きに `mecab-python3` と `ipadic` を要求する。**
   **SudachiPy と別の形態素解析器をもう1つ抱える**ことになり、
   「tokenization は SudachiPy」という求人要件への当て方そのものが濁る

**BCCWJ は「同梱しない・取得スクリプトにする」で入れる。** これは PLAN.md §2-3 が
JMdict について既に決めている扱いと同じ形で、**新しい方針ではなく既存方針の適用**である。

- `data/frequency/` は `.gitignore` に入れ、**語彙表そのものはコミットしない**
- 取得スクリプトを置き、**出典・版・取得日・利用条件を README とスクリプトの両方に書く**
- **段階（tier）は頻度の分位から自作する。** PLAN.md の
  「難易度の区分は語の頻度から自作し、『日本語能力試験の水準におおよそ対応』という表現に留める」に従う

> **再配布の可否が書かれていないものを、書かれていないまま同梱しない。**
> 第1週に japanesecompass.com の差分を「裏取りできなかったので成立しない」と扱ったのと同じ扱いをする。
> **公開リポジトリは、判断を間違えたときに取り消せない場所である。**

### BCCWJ は書き言葉のコーパスである（限界を先に書く）

### 引きの落とし穴と、埋め方（89.7% → 96.6%）

**Sudachi の正規形をそのまま引くと、評価データの内容語145種のうち 89.7%（130件）しか当たらない。**
外れ方に構造があった。

| 外れた理由 | 対処 | 効果 |
|---|---|---|
| 数詞（`6` `25`）— 一覧は `一` `二` と書き、こちらは数字のまま | **`exempt_pos` に `名詞,数詞` を追加**（145件中4件） | 除外 |
| 複合語（`会議室` `日曜日` `報告書`）— **こちらは長い単位で切り、BCCWJ は短単位** | **長単位の表を引き、無ければ A単位に割る** | — |
| 表記ゆれ（`御願い`／`お願い`、`すむ`／`済む`） | 正規形 → 表層 の順で引く | — |

**すべて入れたあとの当たり率は 97.2%**（数詞を除外した分母141件のうち137件。2026-08-11 実測）。
**89.7% と 97.2% は分母が違う**——前者は数詞を含む145種、後者は数詞を除いた141種である。
**残る4件は表記ゆれと1件の造語**（`ラフル` `すむ` `お疲れ様` `かける`）で、**「不明」としてレベル内に数える。** 甘い側だが、
**`unusable_verdicts` と同じ扱い**——規則が推測せざるを得ないときは**失敗を作らない方向へ倒し、
推測した件数を結果の隣に必ず出す。**

### 複合語の穴は、長単位の一覧を足して塞いだ

**`明日の会議室で資料を確認します。` が beginner で「大幅超過」になっていた。**
原因は `会議室` が短単位の一覧に無く、**部品の最大＝`室`（段階5）**を採っていたため。
`室` は単独ではほとんど使われないので段階が高く、**`会議室` という日常語が巻き添えになっていた。**

**「部品の最大」は、片方が接尾辞的な1字語のときに壊れる。**
対処は **BCCWJ の長単位語彙表（LUW・同じ出典・DOI 10.15084/00003212）も引く**こと。
**こちらの切り方（Sudachi の mode C）と単位が揃う**ので、原理的にこれが正しい。
「部品が1字なら最大から除く」は場当たりで根拠が書けず、「複合語は不明に倒す」は判定の放棄である。

**引く順番は「単位が合う順」であって「速い順」ではない。**

1. 短単位の表（普通の1語）
2. **長単位の表（複合語）** ← ここが抜けていた
3. A単位に割って部品の最大 ← **compound 自体を誰も知らないときだけ**

| 表 | 見出し | 段階1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 短単位 | 112,186 | 1,678 | 1,719 | 4,930 | 7,482 | 96,377 |
| 長単位 | 484,981 | 7,293 | 14,997 | 97,313 | 365,378 | （保存しない） |

**長単位は最後の切り（95%）までしか保存しない。** 内容語が210万件あり、
ほぼ全部が1〜2回しか出ない一回性の複合語なので、**全部持てば 100MB の表になって、
「無い＝珍しい」で既に答えが出ている問いに答えることになる。**

**各表は自分の被覆で切る。** 長単位の段階は「**長単位の中でどれだけ普通か**」を意味する——
`会議室` と `猫` を1つの表で比べるのは、コーパスが別々に数えたものを並べることになる。

**結果**（判定の例）

### 1発目の遵守率を測った（2026-08-11・90返答）

実行記録：`evals/runs/20260811-1856-level-compliance.json`

| intermediate | 100.0% |

**beginner は同じ条件で2回測っている。** 疎通確認のつもりで先に beginner だけ回した

### 台本は評価データを使わずに新規に書いた

[evals/script.py](../../evals/script.py)。6場面 × 5ターン。**1行も `data/evaluation` から採っていない。**

- 採れば **`test` の文を会話プロンプトに通す**ことになる。`test` は今月1回しか触らない
- そもそも**会話にならない**。評価データは孤立した文で、ここで要るのは
  **相手の開始文から自然に続く5往復**である
- **わざと正しめの日本語で書いた。** これは直される材料ではなく相手に喋らせるための呼び水で、
  誤りだらけの台本は「誤りにどう反応するか」を測ってしまう——それは訂正エンジンの問いである

### 超過した語は3つだけで、うち1つは学習者自身が使った語だった

`エンジニア`（2回）・`かしこまり`（2回）・`何時ごろ`（1回）。

**`エンジニア` は台本の学習者が `エンジニアです。` と言った直後に、相手が受けて使った語である。**
**学習者が自分で持ち込んだ語を「レベル超過」と数えるのは、測りたいものと違う。**
会話履歴に出た語を免除する案は**1行で書けて、効果も測れる**（免除の有無で遵守率がどう動くか）。
**ただし Day 4 の枠ではない。** 検証ノード②を入れて再生成後の数字が出てから、
**独立した前後比較として測る**——第1週 design.md が丁寧さの下限について書いたのと同じ理由で、
**再生成の効果と混ぜない。**

### ついでに見えたこと：`する` が内容語に入る

`確認します` は `確認`（名詞）＋ `し`（動詞・**非自立可能**）に割れ、`し` も内容語として数えられる。
**`する` `いる` `ある` はどの段階でも出るので、分母を膨らませて比率を下げる**——
助詞を除いた理由（比率がゼロに寄って難しい返答が検査を通る）と**同じ形の穴**である。
**段階の出どころが決まったら、`非自立可能` を除外するかを実測で決める。**

### 1-b. `score_min` の決め方を書いた（2026-08-14・`config/thresholds.toml [retrieval]`）

単調性の問題（「正解 id の再現率」は `score_min` を下げるほど上がるので `score_min = 0` が最良になる）を、
**再現率のほうを先に固定して向きを反転させる**ことで解いた。

> `score_min` ＝ **閾値決めの標本のうち根拠がある8件について、注釈した記事のいずれかが
> 上位3件に、かつその値以上で残る件数が `recall_floor_items` 件を下回らない範囲で、最大の値**

- **候補は実測されたスコアそのもの＋0**。連続値を掃かないので「最大」が必ず存在する
- **`recall_floor_items = 7`（8件中7件、＝87.5%）。** 6件にしない理由は誤りが非対称だからで、
  これは `[rewrite_too_far]` に既に書いた原則と同じ——**捨てられた正しい訂正は学習者から見えない**ので、
  緩い閾値より悪い。7件は「1件までなら根拠を失ってよい」、6件は「4分の1まで失ってよい」になる
- **0 より上のどの値も 7件に届かない場合は `score_min = 0` とし、
  「この規模のリファレンスでは③を運用できなかった」と報告する。** 下限を下げて発火させない
- **該当なし2件は選定に使わない。** 2件では何も分離できず、その2件が棄権するように選べば
  2点への当てはめになる。選ばれた値における棄権数を**診断として報告するだけ**にする
- **`score_min` 自体は 8/15 に測定と併せて書く。** いま書かないのは意図的で、
  `config.threshold()` はファイル名付きの `KeyError` で落ちる——値が存在しないまま③を動かそうとしたら、
  黙ってデフォルトに落ちるのではなく止まるべきである
- **公開する分母（16と4、閾値側の8と2）はテストで用紙に結んだ。** 注釈を1件 `none` から記事に変えれば
  README と用語集の `n` が黙って嘘になるので、`tests/test_retrieval_kit.py` が赤くなるようにした
