## なぜ今これをやるか

### 1. README が測っていない数字を1つ持っている

**2026-09-02 に、振り返り画面に `Reference:` が1度も出ないことが分かった。**調べた結果：

- **検索は動いている。** 記事はプロンプトに届いている
- **モデルが `grounding_ids: []` を返している**（実際の応答で確認）
- 理由①：**上位3件に正解の条が入らない**ことがある（「を→に」の `grammar-001` は6位だった）
- 理由②：**`correction/engine.py:147` に「grounding_ids は常に空配列」という古い指示が残っている。**
  152行目のコメントは「最後の箇条書きを置き換える」と書いているが、**コードは追記しているだけ**で、
  組み上がったプロンプトには**矛盾する2つの指示が同居**している
- **実測は 21/40（52.5%、test 分割、8/20 のラン）**

**README 87行目は 9/2 に直した**（無条件の「引用する」→ 実測値と「半分は出ない」の明記）。
**直っていないのはプロンプトである。** 9/20 の DoD は
「文法リファレンスを検索して**根拠を示す**（RAG）＋検索の当たり率も測っている」であり、
**当たり率（81.2%）は測ってあるが、「実際に引用したか」は 52.5% のまま放置されている。**

### 2. 直すと、公開している数字が全部動く

**ここが本題である。** プロンプトを直せば訂正の出力が変わりうるので、
**判定の正しさ・余計な直しの率・引用率のすべてを測り直す必要がある。**

**そして測り直しは、held-out の規律に触る。** README は
「**プロンプトと閾値は dev だけで調整し、test は最初と最後にしか触らない**」と公開している。
**もう一度 test を回すことは、その「最後」を使い直すことである。**

**この判断を黙って行わない。** 取りうる道は3つで、**どれを選ぶかがこの作業単位の最初の決定**になる。

| 案 | 中身 | 代償 |
|---|---|---|
| **A** | プロンプトを直し、**dev で測って test も1回だけ回す**。README の数字を全部更新し、**「最後の test 実行は 9月に行った」と明記** | test を2度目に触ったことが公開される。**理由つきで書けば説明可能**だが、規律の売りは弱くなる |
| **B** | プロンプトを直し、**dev だけで測る。**引用率は**dev の数字として公開**し、test の表は 8/20 のまま据え置く | 表の中に**別のプロンプトで測った行が混ざる**。混ぜないよう書き分ける手間が要る |
| **C** | **直さない。**欠陥を README に書いたまま 9/20 を迎える（9/2 の記述で既にそうなっている） | 「引用する」が**半分しか働かない実装**のまま。ただし**嘘は無い** |

**推奨は B。** 理由は3つ。**①9/13 に人が触る URL を、その直前にプロンプトごと入れ替えたくない**
（訂正の質が変われば、会場での感想も別物を評価することになる）。
**②held-out を2度目に触る判断は、9/20 の締切に追われながら下すべきものではない。**
**③dev で直ったことが確認できれば、「直し方は分かっていて、測り直しの規律を守るために出していない」
と面接で言える**——これは 9/20 の締切より価値が長い。

**ただしこれは推奨であって決定ではない。** **Jun が A を選ぶなら、それも筋が通る**
（DoD の一行を満たしにいく判断であり、README に理由を書けば嘘にはならない）。
