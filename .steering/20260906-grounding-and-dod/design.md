対応する要求: [requirements.md](requirements.md)

**A（test を2度目に回す）は選ばない。**その判断を締切に追われながら下したくない、というのが主たる理由である。

## 1. 直すのはプロンプトの矛盾だけ。検索には触らない

**原因は2つあったが、今回直すのは1つだけである。**

| 原因 | 今回 | 理由 |
|---|---|---|
| **プロンプトに矛盾**（`grounding_ids` は常に空配列、という古い指示が残っている） | **直す** | **バグである。**モデルに二律背反を渡しておいて出力を責められない |
| **上位3件に正解の条が入らない**（`grammar-001` が6位だった） | **触らない** | `top_k` や閾値を動かすと**検索の当たり率（81.2%）が動く**。**1回の作業単位で2つの数字を動かさない** |

**結果として引用率には天井が残る。** 上位3件に条が無ければ、モデルは正しく「引用できない」と答える。
**それでよい**——**測って書く**のがこのプロジェクトの主張であって、数字を上げることではない。

## 2. プロンプトの組み立てを、1つの出どころに直す

いまは**箇条書きを固定文字列で書いたあと、記事があるときだけ `_GROUNDING_BLOCK` を追記**している。
コメントは「最後の箇条書きを置き換える」と言っているが、**コードは追記しかしていない**。

**直し方は「置き換える」ではなく「最初から分岐して組む」。**
箇条書きを list で持ち、**記事の有無で最後の1項目を選んでから join する。**
文字列の後付け置換は、**同じ間違いをもう一度できる形**なので採らない。

**テストで固定するのは出力ではなく矛盾の不在**である——
**組み上がったプロンプトに、「常に空配列」と「引用せよ」が同時に現れないこと。**
これは API を呼ばずに書けて、**今回の欠陥そのものを二度と通さない**。

## 3. 測るのは dev だけ。test は触らない

- **dev 80件**を、新しいプロンプト版（`correction-rag-v3`）で回す
- **比べるのは 8/20 の dev の数字**（同じ分割・同じモデル・同じ採点器）
- **見るのは3つ**：引用率／判定の正しさ／余計な直しの率。
  **引用率だけが上がって他が落ちるなら、それは改善ではない**
- **test の表は 8/20 のまま据え置く。**README には
  **どの行がどのプロンプト版で測られたかを明記**する。**混ぜない**

**壁時計の目安は 30〜40分**（8/19 の実測：dev 80件で API 33分）。**枠は1日分で足りる。**

## 4. 本番への反映は 9/13 より後

**測るのは 9/13 より前、デプロイするのは 9/13 より後。**

**理由**：訂正の出力が変わるかもしれないものを、**人が触る日の直前に本番へ入れない。**
9/13 に集めるのは**感想3件**であり、**その感想が何についての感想なのかが分からなくなる**のが最悪である。
**9/5 に本番が壊れていた**ことも踏まえると、会場前日に触る回数は少ないほどよい。

**例外はひとつ**：dev の結果が「**引用率は上がったが、他の2つが落ちた**」だった場合。
そのときは**入れない**（プロンプトを戻す）ので、9/13 の前後は関係なくなる。

## 5. 9/13 の会場

**前の単位の `I. 当日の手順` をそのまま使う。**新しく設計するものは無い。
**回収するのは感想3件だけ**で、**用紙は英語1枚**（PLAN.md §2-5）。
**その場で書いてもらう**——持ち帰ってもらうと返ってこない。

## 6. 9/20 の締め方

**DoD の各行を「済」か「降ろした（理由つき）」のどちらかにする。空欄を残さない。**
**未実装の2機能**（言い直しの「もう一度」／AI 文字の非表示）は、
**作らないなら理由つきで `functional-design.md` に書く**。**消すだけにしない**——
消すと半年後に同じ議論をやり直す。
