# 要求内容 — 応答速度の改善（2026-08-21）

## 背景

デプロイ先（Streamlit Community Cloud）を疑ったが、**遅さの原因はホストではない**。
手元の Mac・高速回線・プロセスを温めた状態で 1 ターンあたり **14.1 秒**かかっており、
その内訳はすべて Gemini への直列の往復である。ホストを変えても 1 秒も縮まない。

### 実測（2026-08-21、n=5 の中央値、warm）

| 段階 | 中央値 |
|---|---|
| 文字起こし（gemini-2.5-flash） | 3.40s |
| 返答生成（gemini-2.5-flash） | 1.56s |
| 音声合成（gemini-2.5-flash-preview-tts） | 4.34s |
| 訂正グラフ（検索 + LLM + 検証） | 4.78s |
| **1 ターン合計（直列）** | **14.08s** |

初回のみ、これに **15.1 秒**が加算される（torch/chromadb の import 5.39s ＋
埋め込みモデル読み込み 8.55s ＋ Chroma 構築 1.20s）。

**この 15.1 秒は「1 ターン目の訂正の中」で払われている。** 埋め込みモデルが遅延ロードで、
最初に触るのが `record_correction` だからである。したがって 1 ターン目だけ約 29 秒になる。
Cloud ではさらにコンテナ起動と埋め込みモデル約 120MB の取得が乗る。

**一番目立つのは起動、一番重いのは毎ターン。** 5 ターンの会話で 15.1 + 70.4 = 85.5 秒であり、
起動は 18% にすぎないが、**最初の一発で見放される**という意味では起動の重さが最も高くつく。

### 設計と実装が食い違っている箇所

`app/main.py` の冒頭は「訂正は見えないところで集められ、振り返り画面だけが描画する」と書いている。
しかし `record_correction` は spinner ブロックの内側、`render_input()` の**前**で呼ばれるため、
**学習者は会話終了まで見ないもののために毎ターン 4.78 秒待たされている。**
これは速度の問題であると同時に、ドキュメントがコードを説明していない状態である。

## ユーザーストーリー

- 学習者として、話し終えてから相手が返事をするまでの待ち時間が、人と話しているときの
  「少し考えている」に収まっていてほしい。10 秒を超えると壊れたと思う
- 学習者として、**最初の 1 ターンが特に遅いということがない**でほしい。
  最初が一番遅いと、そこで閉じる
- 9/13 のテスターとして、会場で URL を開いてすぐ話し始められてほしい
- 開発者として、速くするために**公開済みの数字が説明できなくなること**は避けたい

## 受け入れ条件

1. **通常ターンが 6 秒以下**（手元・warm・n=5 の中央値）。現状 14.08s
2. **1 ターン目が通常ターンと同程度**であること。現状 約 29s
3. **会話終了時の待ちが 8 秒以下**（5 文の訂正）。並列化の実測は 5.55s（逐次 23.39s）
4. **返答の最初の文字が 1 秒以内**に画面に出ること
5. **訂正の出力が現状と一致すること。** グラフと `correction.check_with_retrieval` は
   同じ答えを返し続ける（**2026-08-21 追記：これを固定しているはずの `tests/test_graph.py` は
   実在しない。** design.md「未解決として記録すること」を参照）
6. **README の公開数字が引き続き実装を説明していること**
7. `ruff` / `mypy` / `pytest` が通ること

## 制約事項

- **訂正パスのモデルと thinking 設定は変更しない。** README の数字はこの条件で測っており、
  変えれば公開済みの数字が実装を説明しなくなる（受け入れ条件 6）。
  **速くしてよいのは「いつ・いくつ並列で呼ぶか」だけで、「何を呼ぶか」は変えない**
- **`gemini-2.5-flash-lite` は使えない。** このキーで 404（`gemini-flash-lite-latest` は
  音声のみ通る）。モデル差し替えによる短縮は当てにしない
- **Streamlit の 1 プロセス 1 エントリを崩さない。** 起動ファイルは `app/main.py` に固定
- **何も保存しない方針を崩さない。** 高速化のためのキャッシュに学習者の発話を含めない
- スコープを広げない。発音採点・ローカルモデル・React 画面は対象外

## やること（実測の効果順）

| # | 内容 | 実測の効果 |
|---|---|---|
| 1 | 訂正をターンから外し、**会話終了時に並列実行** | 毎ターン −4.78s、終了時 23.39s → 5.55s |
| 2 | 埋め込みモデルと index を**起動時にバックグラウンドで温める** | 初回の 15.1s が体感ゼロ |
| 3 | 返答を**ストリーミング表示**する | 実時間は同じ、初字まで 1.56s → 約 0.4s |
| 4 | **文字起こしの thinking を切る**（`thinkingBudget: 0`） | 3.40s → 2.87s |

**1 + 3 + 4 で通常ターンは 3.40 → 2.87、1.56、4.34 が残り、約 8.8s。**
6 秒に届かせるには 5 の判断が要る。

## やるかどうか判断が要ること（設計で決める）

**5. TTS の 4.34 秒をどうするか。** 1〜4 を終えると、残る最大の要因はこれ 1 つになる。

- **案 A：API のまま、入力欄を音声の完成待ちにしない。** 返答テキストが出た時点で
  学習者は次を話せる。実装は小さく、声質は現状のまま。ターンの体感は約 4.5s
- **案 B：ブラウザの `speechSynthesis` に替える。** 往復ゼロ。ただし声が端末依存になり、
  Android の日本語音声が入っていない端末では無音になる。9/13 の会場でこれが起きると
  「音が出ない」というフィードバックが返ってくる
- **案 C：現状のまま**。1〜4 だけで約 8.8s に留める

**推奨は A。** B は会場当日の端末を選べない以上リスクが読めず、
C は受け入れ条件 1 を満たさない。
