## 実装アプローチ

**テキストのみの縦スライスを1本通す。**抽象化は入れない。第3週に FastAPI と LangGraph へ
切り出すことは分かっているが、**今週その形に寄せない**——使われ方が確定する前の抽象化は
作り直しになる。関数を素直に呼び、モジュール境界だけ将来の分割に合わせておく。

```
Streamlit (app/)
   │  st.session_state に会話履歴
   ├──▶ dialogue.reply(scene, level, history) ──▶ Claude API ──▶ 1〜2文
   └──▶ correction.check(sentence, scene, level) ──▶ Claude API（構造化出力）
                                                        │
                                            会話中は表示せず session_state に溜める
                                                        ▼
                                                  終了時に review 表示
```

**訂正は毎ターン走らせるが、表示は終了時。** 今週は同期呼び出しでよい（並列化は第4週の
最適化枠。ここで先に非同期にすると数字の前後比較が取れなくなる）。

## データ構造

[docs/ja/functional-design.md](../../docs/ja/functional-design.md) の定義に従う。今週の範囲では：

**評価データ1件**（`data/evaluation/items.json` の配列要素）

```json
{
  "id": "eval-001",
  "scene": "greeting",
  "learner_sentence": "おはようです",
  "needs_correction": true,
  "corrected_sentence": "おはようございます",
  "reason_en": "The polite morning greeting is a fixed phrase.",
  "split": "dev"
}
```

**訂正の構造化出力**（`correction.check()` の戻り値）

```json
{
  "needs_correction": true,
  "corrected_sentence": "おはようございます",
  "reason_en": "The polite morning greeting is a fixed phrase.",
  "grounding_ids": []
}
```

`grounding_ids` は今週は必ず空配列。第2週に RAG を入れたときに埋まる。
**キーは最初から最終形にしておく**（後から増やすとデータの作り直しが発生する）。

**実行記録**（`evals/runs/YYYYMMDD-HHMM.json`）

```json
{
  "run_id": "20260806-0730",
  "implementation": "baseline",
  "model": "gemini/gemini-2.5-flash",
  "prompt_version": "baseline-v1",
  "n": 40,
  "split": "test",
  "date": "2026-08-06",
  "detection_accuracy": 0.0,
  "over_correction_rate": 0.0,
  "format_compliance_rate": 0.0
}
```

## 訂正の設計（2026-08-04 実装時に確定）

### JSON を自前で解析する（制約デコードを使わない）

LangChain の `with_structured_output` や Gemini の `responseSchema` を使えば JSON は
まず壊れない。**それでも使わない。**

`format_compliance_rate` は「壊れていない JSON であり、かつ理由が英語で返った割合」
（[glossary](../../docs/ja/glossary.md) §5）で、**今週出す3つの数字のうちの1つ**である。
制約デコードにすると JSON 側は構造上つねに適合になり、**測っていない数字を測ったことにする。**
残る言語の取り違えも測れないままで、これは llm-jp-eval の批判記事が挙げた罠そのもの。

副次的な利点として、ベースラインと本実装が同じ解析経路を通る（design.md 冒頭の方針どおり
採点コードが1本で済む）。

### 再試行は「何が壊れていたか」を添える

`temperature = 0` なので、同じプロンプトを投げ直せば同じ壊れた出力が返る。
**再試行が形だけになる。** そこで1回目の出力と「どこが駄目だったか」を会話に足して投げ直す。

### `format_compliance_rate` は1回目の出力で判定する

再試行で直った場合も**不適合のまま記録する**。再試行が書式の失敗を消せるなら、
壊れた件を分母から捨てるのと同じ嘘になる。訂正そのものは再試行の結果を使う
（判定の精度と書式の適合は別々に記録する、という §5 の原則どおり）。

### 理由が英語かの判定 — 引用の中は見ない

助詞を説明するには「は」と書くのが自然で、**引用の日本語まで不適合にすると
良い理由ほど落ちる。** 「」および引用符の中を除いてから日本語が残るかを見る。

| 理由 | 判定 |
|---|---|
| `「は」 marks the topic, so 「が」 sounds odd here.` | 適合 |
| `「ありがとう」は友達に使う言い方です。` | 不適合 |
| `This is 丁寧な言い方ではありません。` | 不適合 |

### モジュール名は `correction/engine.py`

`check.py` にすると `correction/__init__.py` が再輸出する関数 `check` と衝突し、
`correction.check` が関数かサブモジュールか決まらない（実際にテストが壊れて気づいた）。
公開する呼び出しは設計どおり `correction.check()` のまま。

### 振り返りに出せなかった文

2回とも JSON が壊れた文は、[functional-design](../../docs/ja/functional-design.md) の
とおり訂正としては出さない。ただし**件数だけは画面に出す**。黙って消すと
「この文は問題なかった」と読めてしまい、それはこの文について唯一分かっていないことである。

## ベースラインの設計（今週の主役）

**素朴版 = 大規模モデルに1回投げるだけ。** 検証も RAG も形態素解析も無い。

- プロンプトは「この日本語を直して、理由を英語で教えて」相当の1回呼び出し
- **意図的に良くしようとしない。** 素朴版を丁寧に作り込むと比較表の差が縮み、
  第2週以降の実装の価値が見えなくなる。ただし**出力形式だけは同じ JSON に揃える**
  （形式が違うと採点コードが2本になり、そこが不具合の温床になる）
- 測るのは `detection_accuracy` / `over_correction_rate` / `format_compliance_rate` の3つ

**測るのは2回。それ以降は第4週まで触らない。**

| いつ | 対象 | 位置づけ |
|---|---|---|
| Day 4（8/6） | その時点の評価用 **20件** | **暫定。** 配管が通り数字が出ることの確認。README には載せない |
| 8/10（月） | 評価用 **40件**（確定後） | **正式。** README とベースライン比較表に載るのはこちら |

**2回に割れるのは、評価用が 8/8 まで40件に揃わないため。** 60件時点で振った `split` は
**最後まで動かさない**ので、Day 4 で測った20件は最終の評価用40件の部分集合であり、
**評価用に dev の件が混ざることはない。**

**正式測定は検証ノードを1行でも書く前に行う。** 本実装ができてから測ると
「本実装を知ったうえで作った素朴版」になり、比較表そのものが成立しない。

**実行記録には `n` と `split` を必ず書く。** これが無いと、あとから
「README のこの数字は20件のほうか40件のほうか」を復元できない。

## 採点の設計

- **機械採点するのは `needs_correction` の一致だけ。**
  `corrected_sentence` は完全一致で採点しない（[docs/ja/glossary.md](../../docs/ja/glossary.md) §5）
- `format_compliance_rate` は**精度と分けて記録する**。JSON が壊れた／理由が日本語で
  返ったケースを精度の低下と混同しない
- **採点スクリプト自体に pytest を書く。** 採点の不具合はモデルの改善と区別がつかない
- 実行のたびに**評価用から5件を手で照合**する

## 実機確認の結果（2026-08-03・iPhone Safari）

### ① 録音 = 成功（決着）

**テキスト方式には戻さない。音声は予定どおり第3週で載せる。**

**操作感（実機で観察）**

- **押して開始 → もう一度押して停止。** 押しっぱなしではない
  → 画面ではボタンの文言を状態で変える（「話す」／「話し終える」）
- **マイクの許可は、ページを開き直すたびに1回聞かれる**（録音のたびではない）。
  会話の開始時に1回だけなので実用上は問題ない。ただし**テスターへの説明文には必ず書く**

### ② 自動再生 = 成功（決着）

**当初「失敗」と記録したが誤りだったので取り消した。** 音の高さを毎回変える版で再確認した結果：

- **②-A（即時）・②-B（3秒待ち）とも、押すたびに毎回鳴った**
- **②-C（毎回まったく同じ音）だけ、1回鳴ったあとは鳴らなかった**

→ **原因は Safari の制限ではなく、音声の同一性。** Streamlit は音声を内容のハッシュで参照するため、
**同じバイト列を再度描画しても新しい再生が起きない。** 中身が違えば毎回鳴る。

**第3週は `st.audio(autoplay=True)` で組んでよい。** 3秒待った ②-B も毎回鳴ったので、
モデルの応答待ちを挟んでも「ユーザー操作の直後」の扱いは切れない。

**ただし本番で1つ罠がある（第3週で必ず対処する）**

**AI の返事は繰り返す。** 初級者向けの相手役は「はい、そうです。」「いいですね。」のような短い相槌を
返しやすく、**同じ文が2回出れば音声合成の結果も同じバイト列になり、2回目は鳴らない。**
これは②-C で実際に再現した現象そのもので、**学習者からは「たまに音が出ない」と見える。**

対処は、**音声のバイト列をターンごとに必ず変えること。** 末尾に長さの違う無音を数十ミリ秒足すだけでよい。
カスタム JS は不要で、「UI フレームワークを入れない」方針とも衝突しない。

### ③ この時点で確定していること

- テスターへの説明文（第3週4日目）に**「マイクの許可を求められたら Allow を押す」**を必ず入れる。
  **書き忘れると「マイクが動かない」という感想が返ってきて、本当に測りたい訂正の質の話にならない**
  （返事の再生は自動なので、こちらの説明は不要になった）
- `app/audio_check.py` は役目を終えた。**会話画面ができた時点で削除し、
  Community Cloud の Main file path をそちらへ差し替える。** 枠ごと消さないこと —
  サブドメインはアプリに紐づくため、削除すると確保した URL を手放すことになる
- **画面に「発音は見ていない」と1行書く**（第3週、音声を載せるとき）。文面は
  `This checks the words you choose, not how you pronounce them.` 程度でよい。
  **声で話すアプリを渡されたら、学習者は発音も見てもらえると思う。** そして音声認識が
  言い間違いを黙って直した場合、**正しい文字が出るので「発音は通じた」と誤解して持ち帰る。**
  書かなければ感想フォームに「発音が違うのに何も言われない」と返り、
  **本当に測りたい訂正の質の話が埋もれる。** コストはほぼゼロで、
  「測ったことしか主張しない」という方針とも一致する

## 評価データの検証で分かったこと（2026-08-05・60件）

候補生成は [evals/generate_items.py](../../evals/generate_items.py) で自動化し、**ラベルは付けさせない。**
モデルに文もラベルも決めさせると、`false` の件が「そのモデルが自然だと思う文」になり、
**`over_correction_rate` を最も自分に甘い題材で測ることになる。** 候補には
`intended_label`（そう作れと指示した内容）だけを持たせ、判定はネイティブ検証で確定させた。

### ネイティブ検証で判定が変わった件

**60件中8件（13%）** で `intended_label` が覆った。**この割合自体が報告に値する数字**であり、
「候補生成は自動化し、全件を検品した」という方法論が形だけでないことの証拠になる。

| 変わった向き | 件 |
|---|---|
| `true` → `false` | ごきげんよう。／良い朝ですね。／あなたはこの本を持っていますか。／あなた、どこですか。 |
| `false` → `true` | 寒いですね、今日。／名前は？／すみません、トイレはどこ？／今日、残業できます。 |

### ラベルより、直した文のほうが誤りが多かった

判定が合っていても `corrected_sentence` が使えない件があった。**評価データとしてはこちらのほうが厄介で、
機械採点に出ないので気づかれない**（§5 のとおり直した文は完全一致で採点しない）。

- `スーパーに買い物します` の直しに「を」が落ちていた
- `良い朝ですね` を「いい天気ですね」に直そうとしたが、**直した文のほうが不自然だった**
- `部長、話したいことあります` に「に」を足そうとしたが、**呼びかけの「部長、」は正しく、直しのほうが誤り**

### 「あなた」を理由にした `true` は成立しなかった

生成された45件のうち8件が「あなたは不自然」を理由にしていた。**1つの型が判定の正しさを支配する**うえ、
検証の結果その理由自体が通らなかった（`あなたはこの本を持っていますか` は `false`）。
不自然に見えるのは語順か直訳のほうなので、**理由はそちらを名指しする**。glossary §2 に書き戻した。

### 丁寧さの下限は場面ではなく相手で決まる

候補の段階で、同じくだけ方が `true` と `false` に分かれていた（`これ、いくら？` は `true`、
`これ、ください。` は `false` など）。**放置すると2つの主要指標がどちらに倒したかの数字になる。**
検証で「トイレはどこ？は同僚には良いが店員には直す」と判明し、**相手による3段階**に確定した。
glossary §2 の表がそれで、Day 5 の追加60件はこの規則で作る。

## 追加60件で分かったこと（2026-08-07・Day 5）

### 生成プロンプトを v2 に上げた

**v1 の生成プロンプトは glossary §2 の判定基準を1つも渡していなかった。** 丁寧さの3段階も
「あなた」の規則も **Day 3 の検証で決めて glossary に書き戻したのに、生成側は更新していなかった。**

結果、v1 の候補60件は **14件（23%）で判定が覆り、うち12件がその2つの規則によるもの**だった
（Day 3 の覆りは 8件＝13%）。**同じ検証を2度やっていた**ことになる。

| | v1 | v2 |
|---|---|---|
| 判定が覆った件 | **14 / 60（23%）** | **7 / 60（12%）** |
| うち丁寧さの下限・「あなた」由来 | 12 | 1 |

v2 で渡すようにしたのは3つ。**①場面ごとの丁寧さの下限**（`dialogue/scenes.py` の
`POLITENESS_FLOORS`。glossary §2 の表をコードに置いた）**②「あなた」は欠陥ではない**
**③文は書かれたとおりに判定する**（「本当はこう言いたかったはず」で `true` にしない）。

**ラベル付けの権限は動いていない。** 生成側に**基準**を渡しただけで、**ラベル**は相変わらず
付けさせていない（`intended_label` のまま）。訂正のプロンプトにも触っていないので、
**ベースライン比較は影響を受けない。**

### 監査2周で分かったこと

サブエージェント2体（言語の正しさ／データセットの設計）に独立して監査させ、2周回した。

| | 差し替え | 修正 | 判定 |
|---|---|---|---|
| 1周目 | 14件 | 6件 | — |
| 2周目 | 3件 | 11件 | **条件つきで可** |

**1周目で最も効いたのは重複の指摘。** 完全一致の重複はゼロだったが、
**「一方を直せるエンジンはもう一方も必ず直せる」件が20件**あった。とくに
`corrected_sentence` が既存件の直しと**文字列一致**する件が5件（`手伝ってくれてありがとう。`
`感謝しています。` など）。**学習者の文が違っても、直しが同じなら測っているものは同じ。**

**2周目で最も効いたのは「直した文が不自然」の指摘。** Day 3 と同じ失敗が再発していた
（`大変、荷物でした` → `大変な荷物でした` は文法的には正しいが、荷物を運んでもらった礼としては
言わない）。**直した文は機械採点に出ないので、読まなければ永久に残る。**

**やり過ぎた修正も指摘された**：`それ、手伝って。` の直しを `〜ていただけますか` にしていた。
**glossary §2 は段階Cに です・ます までしか求めていない**のに、直しだけ敬語に上げると
**訂正エンジンの目標値を黙って引き上げる**ことになる（既存の eval-055 とも食い違う）。`〜てください` に戻した。

### 誤りの型を数えたら、偏りが見えた

120件を型で数えて初めて分かったこと。**助詞が26件（29%）で、うち「に ⇔ で」だけで6件**あった。
`detection_accuracy` が「助詞を検出できるか」の数字に寄る。差し替え後は助詞21件・に/で 3件。

**逆に1件も無い型もあった**：助数詞・否定形・自他の対・授受の向き・敬語の向きの5つ。
差し替えで **敬語の向き2件・自他の対1件・授受1件・否定形1件**が入ったが、
**助数詞は最後まで入らなかった**（`--focus` で名指しで頼んでも、モデルは慣れた誤りに戻る）。
**測っていない型があることは、隠さず先に書くほうが強い。**

### `--focus` を足した（当初の設計には無い）

差し替え用の候補を「この型で」と指定して生成する引数。**9月に250件へ増やすときにも要る**——
件数を増やしても型が偏ったままなら、増えるのは測っていることの量ではなく同じことの繰り返しになる。
ただし上記のとおり**指示どおりの型が返る保証は無い**ので、生成後に数え直す工程は消せない。

### ネイティブ検証の結果（2026-08-08）

**機械の事前検品が提案した60件のラベルのうち、3件が覆った。3件とも `false` → `true`。**
**向きが揃っているのが重要で、機械は一貫して「直さない」側に倒していた。**
そのまま採用していたら `over_correction_rate` が実力より良く出ていた。

| 学習者の文 | 機械 | ネイティブ | 直した文 |
|---|---|---|---|
| `私は待ちます。` | そのまま | **直す** | `私は待っています。` |
| `この資料、確認しますか。` | そのまま | **直す** | `この資料をご確認いただけますか。` |
| `お仕事、何？` | そのまま | **直す** | `お仕事は何でしょうか？` |

**先の2件は、機械の提案を伏せて答えてもらった。** アンカリングを避けるためで、
2件とも外れたことが**「基準が人に伝わる形になっていない」ことの証拠**になった。
これは 8/9 の第二採点者との `rater_agreement` と同じ性質の数字である。

### 3件のうち2件は、ラベルではなく基準のほうが誤っていた

**個別の判断ミスではなく、glossary §2 の定義が足りていなかった。** ここが今日いちばん重い発見。

| 覆った件 | §2 のどこが足りなかったか | 書き戻した内容 |
|---|---|---|
| `この資料、確認しますか。` | 段階Cを「です・ます があればよい」とだけ書いていた | **です・ます で足りるのは自分の動作。上司に相手の動作を求める文は尊敬語・依頼形が要る**（`少し考えます` が `false` のままなのは自分の動作だから） |
| `お仕事、何？` | 段階Bの下限を「お／ください／です／ます のどれか1つ」と書いていた | **「お」だけでは足りない。** 「お」は語を丁寧にするだけで文の丁寧さを決めていない。**例外は言いさし**（`お名前は。`） |

**ラベルが動いた既存件は無い。** 動いたのは既存2件の**直した文**だけで、機械採点は
`needs_correction` しか見ないので**測定への影響はゼロ**。

- `eval-055` `資料を見せて。` の直しを `資料を見せてください。` → **`資料を見せていただけますか。`**
- `それ、手伝って。` の直しを敬語へ戻した（8/7 に監査の指摘で `〜てください` に下げていたが、**その向きが逆だった**）

**監査を2周回してもこの2つは出てこなかった。** サブエージェントは §2 の**字面には忠実**で、
だからこそ**字面が間違っている場所は指摘できない**。基準そのものの誤りはネイティブにしか見つけられない
——**この工程を飛ばせない理由が、実例として1つ増えた。**

### 内訳を戻した

3件の反転で **48:12** に崩れたので、監査が落とすべきと指摘していた `true` を3件落とし、
`false` を3件入れて **45:15** に戻した（場面ごとの配分も `BATCH_PLAN` どおり）。

| 落とした件 | 理由 | 入れた件 |
|---|---|---|
| `お名前は何を言いますか？` | 直した文がバッチ内の別件と完全一致（最後の衝突） | `名前は何ですか？` |
| `今どこがいますか？` | `今、あなたはどこにありますか？` と近い重複 | `電車、遅れていましたか？` |
| `私は会議を持っています。` | `持つ` の直訳が120件で4件目 | `資料はコピーしました。` |

`電車、遅れていましたか？` は**助詞を落とした `false`** ＝ 助詞の欠落を直す `true` が多数ある中で、
**訂正エンジンが助詞の補完を過剰般化していないか**を測る件になる。

### 120件に統合した

`eval-061`〜`eval-120` を付与し、`split` は **`start_index=60` から続きで割った**
（Day 3 の60件の `split` は1件も動かない）。結果は **dev 80 / test 40、場面ごとに 2:1**。
機械点検（`tests/test_evaluation_items.py`）は全件通過。

**`test` 側の内訳は `true` 27 / `false` 13。** `over_correction_rate` を `test` だけで見ると
**分母13件＝1件が7.7ポイント動く。** README には `n` を必ず併記し、
**`test` 単独の値だけを載せない**こと（120件全体の値と並べる）。

### `over_correction_rate` が 57.1%（7件中4件）

**素朴版は、そのままで自然な文の半分以上を直しに行った。** これは PLAN.md §2-4 が

直すべき13件を全部直すのは、**全部直しに行くモデルなら自動的に達成できる。**
実際 `over_correction_rate` が 57.1% なので、この 100% は精度ではなく
**直す方向に倒れている**ことの裏返しとして読むのが正しい。**2つの指標は必ず並べて出す。**

### 英語判定の規則を Day 4 に直した（数字が動いた）

最初の実装は「引用符の外に日本語が1文字でもあれば不適合」だった。**20件中9件が不適合になり、

`format_compliance_rate` は 55% と出たが、**日本語で返った件は1件も無かった。**

- 指標の名前は「理由が英語で返った割合」なので、**引用の作法を測っていたのは定義違反**
- **llm-jp-eval の批判記事が挙げた「言語の取り違え」の罠を、逆向きに踏んでいた**
- 割合による判定に変更（閾値は `config/thresholds.toml` の `reason_language`）。
  引用符なしで日本語が残った件は `japanese_left_unquoted` として実行記録に残すが**数えない**
- glossary §5・§7（ja / en）に書き戻した

**この修正の前に取った実行記録は削除した。** 採点規則が変わっており、
**同じスクリプトで再現できない記録を残すほうが害になる**（残せば、あとで
比較表に混ぜてしまう）。同じ理由で実行記録に **`scorer_version`** を足した——
採点側の規則で動いた数字は、プロンプトの版だけ見ていると「モデルが変わった」と読める。

「素朴だから」ではなく「情報が足りないから」外し、**比較表が「場面を教えたかどうか」の表になる。**

## 採点キットと文法リファレンスで分かったこと（2026-08-08・Day 6）

### 一致率の20件は `dev` から採る

[glossary](../../docs/ja/glossary.md) §5 の `rater_agreement` は「両方が採点した20件の一致率」としか
書いておらず、**どの分割から採るかが決まっていなかった。** `test` から採ると、採点のために自分が
評価用の中身を読むことになり、第2週以降のプロンプト調整がその記憶に汚染される（§7）。
一致率は**2人が尺度を同じに読んでいるか**を見る数字なので `dev` で成立する。§5 に書き戻した。

**副作用が1つあった。** §6 は「40件を採点し、うち20件を第二採点者が」と書いていたが、
20件を `dev` から採ると**40件の内数ではなくなる。** 人手の採点は合計60件になる。§6 も直した。

### 場面は「丁寧さの段階」ではなく、モデルに渡した文言そのものを刷る

最初は採点キットに丁寧さの段階（§2 の A/B/C）だけを刷っていた。これは**相手を特定しない**——
段階Bの文言は「初対面の相手**または**店員」であり、2択のまま採点者に渡ることになる。

実物で問題が出た。キット #13 は「良い一日。→ **いってらっしゃい！**」で、この直しは
**相手が出かけるところ**でなければ成立しない。その情報は `scene_brief`（モデルに渡した文言）に
あり、丁寧さの段階には無い。**情報不足で割れた採点は、尺度のずれではないので §6 を直しても直らない。**

### 文法リファレンスの例文を評価データからずらした

初稿は、45件の `true` のうち**30件の学習者文をそのまま例文に使っていた。**
これだと第3週の `retrieval_hit_rate` が**文字列の一致で当たる**——高い数字が出たうえで、
実際の学習者の発話には移らない。llm-jp-eval への批判記事が挙げた罠と同じ形である。
規則と ✗/✓ の対比は残したまま、例文を別の文に差し替えた。

### 監査で見つかった、リファレンス側の誤り

**規則を厚く書くと、規則そのものが嘘になる。** 実際に出たもの：

- **「スーパーで買い物します」に 「を」 が要る、と書いていた。** これは正しい文であり、
  そのまま RAG の根拠になれば**正しい文を直しに行かせる**（`over_correction_rate` が悪化する）
- **「です は名詞にしか付かない」と書いていた。** 「寒いです」があるので嘘で、同じ8本の中の
  grammar-004 と矛盾していた
- **「私を助けて、ありがとう」の誤りは 「私を」 だ、と書いていた。** 「私を助けてくれてありがとう」は
  自然な文で、欠けているのは 「くれて」 のほう。**理由が間違っていると §6 では「誤り」に採点される**
- **助詞の省略を「です・ます と混ぜると不自然」と一般化していた。** 「コーヒー、飲みますか」は普通なので、
  `が`（あります・要ります・必要です の前）に限定した
- **「隣人さん」を「日本語は関係で人を呼ばない」と説明していた。** 部長・先生・お客さん があるので嘘。
  eval-052 の理由（「部長、」は問題ない）と正面から矛盾していた

### 「このままでよい」の根拠を足した（2周目で塞いだ）

1周目の8本は**ほぼすべてが「これは誤り」の説明**で、**「この文はこのままでよい」の根拠になる
記述が1つも無かった。** `over_correction_rate` を15%以下に抑える設計なのに、
**根拠の側が直す方向にしか効かない。** 30件の `false` はそこを測るためだけに存在するのに、
検索して引ける裏付けが無ければ、モデルは黙る判断を根拠づけられない。

2周目で6箇所足した。「あなたはこの本を持っていますか。」は正しい文である（grammar-003）／
「待ちます」と「待っています」はどちらも誤りではない（grammar-006）／
段階Aで普通形は誤りではない（grammar-008）／「を」の省略は丁寧な話し方でも自然（grammar-002）／
「掃除します」も「掃除をします」も普通（grammar-005）／「少し考えます」は上司にもこのままでよい
（grammar-007）。

### まだ埋まっていない穴（第2週以降）

- **例文の流用が完全には消えていない。** 90件の `true` のうち、学習者の文が11件・
  正解の直しが14件、**文字列としてリファレンスに残っている**。残っているのはほぼ定型句
  （おはようございます／はじめまして／お願いします／お先に失礼します）で、
  **定型句を載せない定型句の説明は書けない**ため、ここは許容した。
  ただし **`retrieval_hit_rate` を測るときは、この17件を別に集計する**——
  そうしないと「文字列が一致しただけ」と「文法で当てた」が混ざる
- **1話題に複数本が当たっているのは「を／が」「ています」「丁寧さ」「定型句」の4系統。**
  残りは実質1話題1本で、相互参照はポインタであって2本目の説明ではない。
  第3週に Chroma へ載せるときに再点検する

## 判断が必要になったら

- **実機確認（8/3）で①録音が動かない場合** → 音声を諦めてテキスト方式に切り替える。
  PLAN.md §3「降ろす順番」の1番を第1週の時点で適用する。この判断は先送りしない
- **②自動再生だけ動かない場合** → **テキスト方式には戻さない。**「再生ボタンを押す」方式に落として第3週へ進む。
  iOS Safari の自動再生ブロックは**ブラウザ側の方針**であり、実装で解決できるものではない。
  録音・文字起こし・読み上げは残るため、降ろす対象は「自動再生」だけに限定する
- **確認は必ず HTTPS の URL で行う（誤判定の防止）** — マイク取得（`getUserMedia`）は
  セキュアな文脈でしか動かない。PC で `streamlit run` して iPhone から `http://192.168.x.x:8501` を開くと、
  **コードが正しくても録音は失敗する**。これを①の失敗と誤読すると、不要なテキスト方式への撤退を招く。
  第3週予定の Streamlit Community Cloud へのデプロイを**1つ前倒しして**、その URL で確認する
- **評価データ作成が3時間を大きく超える場合** → 90件に減らし、誤差の但し書きを厚くする
  （降ろす順番の3番）。**分割の比率は変えない**
- **テスター候補の前向きな返事が3人未満** → 第2週の頭に計画を見直す
